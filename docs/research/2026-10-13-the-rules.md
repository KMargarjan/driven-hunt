# The rules: a shot that is REFUSED before it is taken

Task 171. 2026-10-13.

## What the system must do

Karen's words, in the order she said them:

* **2026-10-11, about beaters:** *"No penalty now we need simplify scope, thye just can't shoot them"*
* **2026-10-12, about a hunter who is not at his stand when the 15 s pick window ends:** he
  *"CAN'T SHOOT until he steps in"* -- and **no punishment**
* **2026-10-10, about the rifle:** *"Rifle they has to purchase default is double barrel shotgun with
  limited ammon per round"*
* **2026-10-10, about a red deer with no licence:** *"they can aim but no shooting happening"*
* **2026-10-12:** a piglet is a **penalty** (already built in task 170: `POINTS.KIND.cub = -10` plus
  the coins line)

So four rules, and three of them are the same shape: **the trigger does nothing, and nothing is
taken away from the player**. That shape is new in this game. Every rule the drive has had until
today -- the safety arc and the tie to a tree (`Match.Penalty`), the piglet's -10 -- lets the shot
happen and then **charges for it**.

Numeric targets:

| | |
|---|---|
| shells per drive, shotgun | **12** per ammo kind, refilled once per drive (`Shotgun.CONFIG.DRIVE_SHELLS`) |
| the stand's circle | **12 studs** (`Match.CONFIG.STAND_RADIUS_STUDS`, the radius task 166 measured and Karen accepted as `ForestTest.PICK.standRadiusStuds`) |
| a refused shot costs | 0 shells, 0 points, 0 coins, 0 muzzle flashes, 0 pellet casts |
| what the player gets instead | one dry click (`rbxasset://sounds/clickfast.wav`, measured loading in this place in task 124: 0.29 s) and one short line on the readout |
| how long a refusal takes to decide | one call, on the fire path, which already rate-limits at `FIRE_RATE_LIMIT` |

## Sources

**1. OpenTTD -- `CommandCost`, and a command that is tested before it is executed.**
<https://github.com/OpenTTD/OpenTTD> (`src/command_type.h`). **GPL-2.0-only**, actively maintained
(pushed 2026-10-12, 8.4k stars; the GitHub API answers `NOASSERTION` for its licence field because
of the shape of its `COPYING.md` -- the project states GPL v2 itself).
Quoted from `src/command_type.h`:

> "Common return value for all commands. Wraps the cost and a possible error message/state together."

and the flag that separates the two phases:

> "Execute, ///< execute the given command"

**What it does well:** every action in OpenTTD is a *pure question first* -- run it without
`Execute` and you get a `CommandCost` that is either a price or an error, and the world is not
touched. Our `(ok, reason)` pair is that return value, and "decide, then commit" is why a refused
shot can cost nothing: the reducer `StateMachine.apply` already returns a NEW state rather than
mutating one, so the owner can simply decline to keep it.
**What it does badly for us:** the test and the execution are the same function in OpenTTD, so the
rule and the effect live together. Here the facts come from three different owners (the drive, the
world's stands, the player's profile), so they cannot be one function.
**Could not verify:** the two-phase contract is not written down in `command_type.h` beyond the
enum comment above; the fetch of that header found no sentence stating "test first, then execute",
so that reading comes from the flag's name and its use, not from a quote.

**2. Luanti (formerly Minetest) -- `core.is_protected` and `register_on_protection_violation`.**
<https://api.luanti.org/core-namespace-reference/>, engine <https://github.com/luanti-org/luanti>.
Engine **LGPL-2.1-or-later** (documentation CC-BY-SA), actively maintained (pushed 2026-10-10,
13.7k stars). Quoted:

> "Mods should use core.is_protected when testing whether a player owns a specific position, and
> protection mods simply override this function."

> "This function is called by builtin and mods when a player violates protection at a position (eg,
> digs a node or punches a protected entity)."

**What it does well:** one *overridable predicate* per question, asked by whoever is about to act,
and the thing that OWNS the answer is not the thing that acts on it. That is exactly this repo's
injected-provider idiom (`Weapon.setArmingPolicy(Match.mayCarryWeapon)`,
`Weapon.setDriveLineProvider(Match.driveLine)`), so the borrow is a confirmation rather than a new
pattern: **three more providers, one question each.**
**What it does badly:** `is_protected` is advisory -- the engine does not enforce it and every
caller has to remember to ask. That is a mod ecosystem's problem and would be a cheat here, so the
asking happens in the one server-side place a shot can come from (`Weapon.onFireRequest`) and the
client is only a mirror.

**3. ioquake3 -- `g_friendlyFire`, which is the pattern we DO NOT adopt.**
<https://github.com/ioquake/ioq3> (`code/game/g_combat.c`). **GPL-2.0**, actively maintained
(pushed 2026-10-12). Quoted from `G_Damage`:

```
		if ( targ != attacker && OnSameTeam (targ, attacker)  ) {
#endif
			if ( !g_friendlyFire.integer ) {
				return;
			}
		}
```

**What it does well:** it is one line, in one place, and it cannot be got round -- every damage
event in the game passes through `G_Damage`.
**What it does badly for Karen's rule:** it is **post-hoc**. The shot is fired, the rocket flies,
the hit is registered, and only the DAMAGE is dropped. Karen asked for the opposite -- *"thye just
can't shoot them"* -- and the difference is visible on the screen: ioquake3's player sees his shot
pass through his team-mate, ours must see the gun not go off. Our own `Match.Penalty` is ioquake3's
shape (judge the shot after it was taken) and it **stays**, for a shot fired *near* a beater; the
new rule sits in front of it, for a shot aimed *at* one.

**4. theHunter: Call of the Wild -- a licence per species.**
<https://thehunter.fandom.com/wiki/Weapons> (proprietary game, nothing to copy; cited as a design
precedent, as `docs/research/2026-10-05-drive-report.md` already cites the same game's harvest
screen). There a weapon class is tied to the animal class it may legally be used on, and the game
refuses the *validity of the harvest* -- no credit, a fine -- rather than the trigger.
**Adopted:** the per-species table as DATA (`src/shared/Licences`), which is the half Karen asked
for (*"they can aim but no shooting happening"*). **Not adopted:** the fine. She asked for no
punishment.

## The pattern adopted, and why

**Decide on the fire path, inside the one owner that already owns a shot, with one pure predicate
per question and one injected provider per fact it needs.**

1. `src/server/Weapon/Rules.luau` -- **pure**: no service, no Instance, no clock, no `Player`. One
   function per question (`Rules.beaterInLine`, `Rules.outsideStand`, `Rules.unlicensed`), plus the
   closed set of reason strings and the one short line each puts on the Hud. One predicate per
   question is rule 3 applied inside a system, and `Match.Penalty`'s own header says why:
   *"four questions in one predicate is how 'one predicate answered two unrelated questions'
   happened in the previous project"*.
2. The **order** is the owner's, not the predicates' -- exactly as `Limits`, `Validator` and
   `StateMachine` are sequenced by `onFireRequest` today and not by each other.
3. The **facts** come from three providers wired at the composition roots and never required:
   `Weapon.setTargetProvider` (what the aim ray hit: a beater? which species?),
   `Weapon.setStandProvider` (this player's stand circle, or nil for "he has none") and
   `Weapon.setLicenceProvider` (what he holds). With no provider wired every answer is "no
   restriction", so a spec -- and a world that wires nothing -- behaves exactly as the game did
   before this task.
4. **Nothing is committed until every gate has passed.** `StateMachine.apply` is pure and returns a
   new state, so the owner computes the aim ray from the PRE-fire state, runs the gates, and only
   then calls `setState`. A refused shot spends no shell, moves no barrel, starts no bolt, fires no
   `ShotFired` and casts no pellet (OpenTTD's test-then-execute, source 1).
5. The **client is a mirror and not a second decider.** It already predicts nothing -- the flash,
   the smoke and the bang all arrive with the server's `ShotFired` -- so "the gun visibly does not
   fire" needs no new client rule at all. What is added is the feedback: the snapshot carries
   `refused = <reason>`, `CameraBoot` plays one dry click, and the Hud prints the line that is
   already carried in `notice`.

## What was NOT built, and why

* **No punishment for either new rule.** Karen said so twice (*"No penalty now"*, *"no punishment"*).
* **No new animal.** The licence rule is proved on a **stub species** -- a part carrying
  `Species = "reddeer"` -- because no deer exists. The boar's own trunk publishes
  `Species = "boar"` (the attribute idiom `Damageable`/`HitZone` already uses), so the rule is live
  rather than dormant and the table's free row means something today.
* **No pooled ammunition.** `START_RESERVE` is per ammo kind in the reducer, and the per-drive
  allowance follows it: **12 Slug and 12 Buck**, refilled once per drive and keyed by the drive
  number so a mid-drive respawn is not a free resupply. A single pool of 12 across both kinds would
  change what `state.reserve` MEANS -- the Hud's readout, the rifle's row and the reducer's three
  reserve sites -- which is a bigger change to the gun than the rule needs. Flagged for Karen.
* **No change to the safety arc or the tie.** They answer a different question (see source 3).
* **No rifle change.** Karen: the rifle is *purchased*; its reserve is `Rifle.CONFIG.START_RESERVE`
  (9) and this task does not touch it. Noted for the shop task.
