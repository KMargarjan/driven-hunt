## What the system must do

From `docs/PROJECT_CONTEXT.md` and `ROADMAP.md` (v1 scope):

1. A **break-action shotgun, two barrels**: fire (one barrel at a time), open, eject, reload two
   shells, close. **Slug and buckshot** selectable.
2. **Third person normally, first person while aiming.** Exactly **one** camera writer.
3. **Hit zones** (Milestone 1.5): head/chest instant, body short run, legs long run. This task only
   has to define the interface the hit-zone system will consume.
4. **The safety rule** (Milestone 1.7): shooting toward the drive line is punished. This task defines
   where that check hooks in, not the punishment.
5. Server-authoritative enough that a client cannot invent kills.

Out of scope here: the hit-zone reaction itself, the penalty, ammo economy, recoil *tuning*, sound,
art, animation — and **all code**.

## Why this note is longer on the camera than on the gun

`docs/PROJECT_CONTEXT.md` lists **six** things that killed the previous project. Two of them are in
exactly this system, and they supply three of its named symptoms: *"Three scripts set the mouse cursor"*, *"One predicate answered two unrelated
questions, so mounting hid both the crosshair and the weapon"*, and *"a home-grown viewmodel system"*
which "produced a run of bugs and was fixed for good only by adopting an established pattern".

A shotgun in third person with first-person aim is the single most owner-tangled thing in the game:
camera, input, viewmodel, character animation, crosshair and weapon state all want to write to each
other. So the ownership question is the design, and the ballistics are the easy part.

## Sources

### 1. Roblox raycasting — `WorldRoot:Raycast` and `RaycastParams`
- <https://create.roblox.com/docs/workspace/raycasting>
- Licence: first-party documentation (creator-docs is CC BY 4.0); the API ships with the engine.
  Maintenance: actively maintained.
- **Good:** the whole hit-detection primitive. `RaycastParams` gives `FilterType` (Exclude/Include),
  `FilterDescendantsInstances`, `IgnoreWater` and `CollisionGroup`; a `RaycastResult` carries
  `Instance`, `Position`, `Normal`, `Distance` and `Material` — `Instance` is what a hit-zone part
  lookup needs. Ray length is the magnitude of the direction vector.
- **Bad / the limit to know:** **"The maximum length is 15,000 studs."** Not a constraint at our
  ranges (a slug's practical range is ~327 studs) but it is a hard edge. The page does **not** cover
  `Blockcast`/`Spherecast` — those are source 2. It also says nothing about *who* should cast; that
  is a security question, source 5.

### 2. `WorldRoot:Blockcast` / `Spherecast` / `Shapecast`
- <https://create.roblox.com/docs/reference/engine/classes/WorldRoot>
- Licence: first-party. Maintenance: current.
- **Good:** confirmed signatures —
  `Blockcast(cframe: CFrame, size: Vector3, direction: Vector3, params: RaycastParams): RaycastResult?`,
  `Spherecast(position: Vector3, radius: number, direction: Vector3, params): RaycastResult?`,
  `Shapecast(part: BasePart, direction: Vector3, params): RaycastResult?`. A swept sphere is the
  cheap, forgiving alternative to N pellet rays if buckshot ever costs too much.
- **Bad:** each returns **one** `RaycastResult?`, not a list, so a single spherecast cannot tell you
  *how many* pellets hit — and "how many pellets" is exactly what buckshot damage is. So buckshot
  stays N rays; the shapecasts are a fallback for forgiveness, not a replacement.

### 3. FastCast2 — the maintained continuation of FastCast
- <https://github.com/Per2iako/FastCast2> · docs <https://weenachuangkud.github.io/FastCast2/> ·
  forum <https://devforum.roblox.com/t/fastcast2-.../4093890>
- Licence: **dual MIT / ART** (both files in the repo). Maintenance: ~1,193 commits; the README
  states plainly *"Because FastCast is no longer actively maintained by EtiTheSpirit, this repository
  continues the project with updates and adaptations."* On Wally as
  `weenachuangkud/fastcast2@0.1.4`.
- **Good:** the standard answer for ballistic projectiles on Roblox — simulates many projectiles by
  stepping raycasts instead of replicating physics parts; raycast, blockcast and spherecast modes,
  parallel scripting, `ObjectCache` pooling, `HighFidelitySegment`, cast visualisation.
- **Bad for *us*, specifically:** it solves **travel time and drop**, which a shotgun at our ranges
  does not have. **(Off-branch context, like the SimplePath comparison below: the boar's 38 studs/s
  and the 400-stud arena are Tasks 18 and 17, neither of which is on this branch, and neither number
  appears in sources 1–9 or in the table below. The argument does not rest on them — at any plausible
  slug speed the flight time across this arena is a small fraction of a second, so a hitscan ray and
  a simulated projectile are indistinguishable.)** Adopting
  it would add a Wally dependency, an `ObjectCache`, a per-shot object lifecycle and a second place
  where hits are decided — for a feature we do not need yet. **Also note the provenance problem is
  the same shape as SimplePath's** (rejected in the boar-ai note, which is **not on this branch**;
  the comparison is context, and the rejection below stands on its own): the canonical FastCast is
  dead and there are at
  least four near-identical FastCast2 forks (`Per2iako`, `Shellworks-Development`,
  `weenachuangkud`, `jaeymo`), with the Wally package published under one of them.

### 4. Viewmodel pattern: character clone parented to the Camera, driven by springs
- <https://devforum.roblox.com/t/fps-using-viewmodels-the-improved-version-parts-2-out-of-3/1129877>
  (author: rokoblox5, 2021) — the widely-copied write-up of the pattern.
- Spring module: **EgoMoose, `rbx-fractality-spring`** —
  <https://github.com/EgoMoose/rbx-fractality-spring> · docs
  <https://egomoose.github.io/rbx-fractality-spring/>. Licence: **MIT**, not archived; a typed
  rewrite of Fraktality's `spr`; Wally `egomoose/fractality-spring`.
- **Good:** the pattern is exactly what the previous project only got right after adopting it. The
  viewmodel is a stripped character clone (**legs, face and accessories deleted**) parented to
  `workspace.CurrentCamera`, positioned every frame from the camera's `CFrame` with a stored offset:
  `ViewModel:SetPrimaryPartCFrame(Camera.CFrame:ToWorldSpace(Offset))`. Aim is a spring between the
  hipfire offset and an offset computed so the gun's `AimPart` sits **where the camera is**; recoil
  is a second spring applied as `HandleTransform * CFrame.new(Recoil.Position) * HandleTransform:Inverse()`,
  with a third spring for camera kick. Damper/speed values in the write-up: aim spring damper 1,
  speed 16.
- **Bad:** `SetPrimaryPartCFrame` is the 2021 API (`PivotTo` is current); parenting to the Camera
  means the viewmodel is **local, unreplicated and invisible to the server**, so it can never be the
  thing that decides a hit; and the write-up is a forum post, not a maintained library — we take the
  **technique**, and the only code we take is the MIT spring.

### 5. Client/server trust — why the server must own the hit
- Roblox security guidance is spread across the docs; the operative fact for this design is
  structural and checkable rather than a quotable sentence: **`workspace.CurrentCamera` is
  "Not Replicated"** (<https://create.roblox.com/docs/reference/engine/classes/Camera>, first-party,
  maintained), so the server cannot see where a player is looking, and **the viewmodel lives under
  that camera** (source 4), so the server cannot see the gun either.
- **Consequence, and it is the whole client/server split:** the client is the only thing that knows
  the aim ray, and the client is untrusted. The server therefore cannot *reproduce* the shot; it can
  only **validate** it. What it can check without the camera: that the player is alive and holds the
  tool; that the barrel had a live shell; that the shot obeys the fire-rate and reload timings; that
  the claimed origin is within a tolerance of the character's actual position; that the claimed
  direction is a unit vector; and that the server's own raycast along that ray from that origin hits
  what the client says it hit, within tolerance.
- **Bad:** this is a *tolerance* game, not a proof. A client that lies about direction only (aimbot)
  passes every one of those checks, because the direction is unknowable to the server. That is
  accepted for v1 and written down here so nobody later believes the check is stronger than it is.

### 6. Roblox units — the stud scale every number below rests on
- <https://create.roblox.com/docs/physics/units>
- Licence: first-party. Maintenance: actively maintained. States **1 stud = 28 cm**, 1 RMU = 21.952 kg.
- **Good:** one authoritative number, already used for the boar. **Bad:** it is a convention, not
  enforced by the engine, so it has to be obeyed deliberately.

### 7. Real shotgun ballistics — *The Maximum Practical Range of Slugs & Buckshot*, Shooting Illustrated (NRA)
- <https://www.shootingillustrated.com/content/the-maximum-practical-range-of-slugs-buckshot/>
- Licence: copyrighted article; **facts and figures cited, no text reproduced beyond short quotes**.
  Maintenance: a dated article, not a living document — but ballistics do not change.
- **Good:** measured figures rather than folklore. Buckshot from a home-defence smoothbore
  *"spreads to 45 inches"* at 30 yards, *"with only a couple pellets in the vital zone"*, and the
  author's conclusion is *"30 yards is my maximum practical range with buckshot"*. A full-choke
  hunting gun *"spreads 15 inches at 30 yards"*. Slugs (Federal Premium Barnes Expander, bead-sighted
  smoothbore, from a rest): *"50 yards: I averaged 4-inch groups"*, *"75 yards: 6-inch groups"*,
  *"100 yards: 10-inch groups"*, against a ~10-inch vital zone, giving *"my MPR is 100 yards"*.
- **Bad:** one author, one gun each, from a rest. Choke changes buckshot spread by 3×, which is why
  the game number is a **band** and Karen's dial, not a derived constant.

### 8. *Myth-Busting: 1″ per Yard Shotgun Pattern Spreads*, The Firearm Blog
- <https://www.thefirearmblog.com/blog/2014/07/04/myth-busting-1-per-yard-shotgun-pattern-spreads/>
- Licence: copyrighted article, figures cited only. Maintenance: 2014, static.
- **Good:** it kills the rule of thumb I would otherwise have used. Measured across stock barrels the
  spread was *"less than .5″ per yard"*, with only a back-bored barrel near the claim at
  *".96″ per yard"*. So "1 inch per yard" is an upper bound for cheap ammo out of a cylinder bore,
  not a law.
- **Bad:** a blog, not a lab. It is used only to bound the spread from below, and source 7 bounds it
  from above: source 7's 45 in at 30 yd is 1.5 in/yd (a deliberately open home-defence load) and its
  full-choke 15 in at 30 yd is 0.5 in/yd. **The band is 0.5–1.5 in/yd**, stated here once and used
  nowhere else in another form.

### 9. ACS (Advanced Combat System) — the off-the-shelf Roblox FPS kit
- <https://devforum.roblox.com/t/acs-advanced-combat-system-robloxs-1-fps-combat-system/1285741>
- Licence: **could not confirm.** It is distributed free by @00scorpion00 and @dusek_br, but I found
  no licence file or explicit licence grant. Maintenance: the forum thread is administrator-managed
  and updated, so it is alive.
- **Good:** a complete, battle-tested first-person combat system — viewmodels, ADS, recoil, ballistics
  and replication already solved, used by a large number of Roblox shooters.
- **Bad, and decisive:** (a) **no confirmable licence** on a public repository is a non-starter;
  (b) it is a *whole game framework*, not a module — adopting it means adopting its camera, input,
  state and UI owners wholesale, which is the opposite of one-owner-per-system chosen deliberately;
  (c) it is a military-shooter kit, and this is a hunt with two shells and a safety rule.

## Pattern adopted, and why

**Client aims and shows; server decides and damages. One writer each.**

1. **Camera — one writer, client.** A single client module owns `workspace.CurrentCamera`. Third
   person by default, first person while the aim input is held, with the transition driven by a
   spring. **Nothing else in the codebase may set `Camera.CFrame` or `CameraType`.** This is the
   rule the previous project broke three times over (`PROJECT_CONTEXT.md`).
2. **Viewmodel — one writer, client, and never authoritative.** Source 4's pattern: a stripped
   character clone parented to the Camera, pivoted each frame to `Camera.CFrame * offset`, with
   aim/recoil/sway as springs from EgoMoose's **MIT** `fractality-spring` (source 4). It is local and
   unreplicated by construction, so it *cannot* leak into hit detection.
3. **Hit detection — hitscan rays, cast on the client for feedback and on the server for truth**
   (sources 1, 2, 5). Slug = one ray. Buckshot = 9 rays in a cone, seeded from a server-supplied
   shot id so client and server draw the *same* pattern. The server re-casts and validates; the
   client's result is only tracers and impact effects.
4. **Not FastCast2** (source 3), with a written reason (rule 2): it solves travel time and drop,
   neither of which exists at 330 studs with a shotgun; it costs a Wally dependency, an object
   lifecycle and a second place where hits are decided; and its provenance is split across four
   forks with the dead original upstream. **Revisit when a projectile actually needs to travel** —
   slugs with drop, or any later weapon.
5. **Not ACS** (source 9): no confirmable licence, and it replaces every owner in the game.

**What is invented, and why it has to be (rule 2).** The **safety rule** — punishing a shot fired
toward the drive line — has no external pattern; it is this game's own mechanic. Its whole content is
a dot product between the shot direction and the drive-line normal, evaluated server-side at the same
moment as hit validation. It is one function and one number (the forbidden arc), and it is the
Architect's to place.

## Addendum, 2026-09-25 (Task 26): the camera, and what sources 4-5 meant in practice

The camera has a full Architect design (`docs/design/camera.md`, section 7 lists its eight sources
with licence and maintenance status). This addendum records only what **building** it measured,
which is what `docs/design/camera.md` section 13 asks the Builder to confirm.

- **`PlayerModule:GetCameras():Disable()` could not be confirmed, because this place has no
  `PlayerModule`.** During Play, `Players.LocalPlayer.PlayerScripts` holds our own modules plus
  `RbxCharacterSounds` and nothing else. So the documented way to switch the stock camera off never
  runs here. `Camera.Rig` sets `CameraType = Scriptable`, watches for a `PlayerModule` appearing
  later, and relies on the **foreign-write detector** (design section 10.1) for the actual proof that
  one thing writes the camera: `foreignCameraWrites == 0` over 121 frames, asserted every run.
- **Source 4 (the viewmodel write-up,
  <https://devforum.roblox.com/t/fps-using-viewmodels-the-improved-version-parts-2-out-of-3/1129877>,
  rokoblox5, 2021, forum post, static since 2021)**: technique adopted, no code copied, and with
  `PivotTo` in place of the post's deprecated `SetPrimaryPartCFrame`. The post assumes an animated
  arms rig and an `.rbxm` weapon; neither exists here, so the "model" is a clone of the code-built
  Tool `Handle`.
- **Source 5 (the camera is not replicated)** held: there is no server half of this system and no
  remote, so nothing about the camera can be a second truth.
- **Two numbers the design left to the screen** were set by looking at it (rule 5):
  `VIEWMODEL_AIM_OFFSET` and `VIEWMODEL_HIP_OFFSET`. The design's -0.9 stud aim offset put the rear
  half of a 4.4-stud handle behind the near plane. Karen's to set.
