# The aim bench: one repeatable instrument for "does aiming at what she sees hit"

Task 307. 2026-10-29.

## What the system must do

Karen's core ask (2026-10-24/25): *"we need to aim in empty space to get hit in head neck or heart
like in real life"* and *"all weapons must feel like real ballistics"*. The question every shooting
task since 280 has tried to answer is one question: **does aiming at the animal the client DRAWS,
plus the real lead, hit -- every gun, every pace?**

Five sessions measured it with five ad-hoc rigs and the counts **disagree on one build**:

| rig | build | rifle, RUN, nose aim |
|---|---|---|
| `<runs-dir>/playtest/check305c` (Playtester, real OS clicks) | 9e2d4718 | **9/10** |
| `<runs-dir>/305d/U2` (Builder, hand-built `FireRequest`) | 5c444dbe + fix | **5/9** |
| `<runs-dir>/305b` (Builder) chest+lead | ea72ffc9 | **4/10** where 305b's own nose read 9/10 |

A 10-shot sample of a ~50 % aim has a 95 % interval roughly 20-80 % wide. **Those three numbers do
not disagree about the game; they are the same number read three times.** So the instrument has to
fix four things: a real sample size, a confidence interval, ONE definition of each aim point, and a
self-check that fails when the rig stops measuring.

Numeric targets, decided here:
* **N = 30 per cell** -- at a true 70 % that is a +-17 pp interval, against +-29 pp at N = 10. It is
  the smallest N at which a 70 % cell and a 40 % cell stop overlapping.
* **a CONTROL cell** (chest centre + `Ballistics.leadStuds`) in every session, and it must read
  >= 50 %.
* **a KNOWN-BAD cell** (nose + one drawn body length of clear air) in every session, and it must
  read <= 20 %.
* **their 95 % intervals must not overlap**, or the whole table is printed `INSTRUMENT SUSPECT`.

## The pattern adopted, and why

**A Python host plus one resident Luau script, talking over `tools/studio_mcp.py`.**

1. **The shot goes through the real client input path and nothing else.** A `mouseButtonClick`
   through StudioMCP's `user_mouse_input` -- the same route the harness's own Task-6 replay uses --
   reaches `UserInputService` -> `ContextActionService` -> `DrivenHunt.Weapon.Fire` ->
   `Weapon.Input.fire`, the client's one firer of `FireRequest`. Every earlier Builder rig built the
   payload itself, which can only ever measure the rig. **Rejected:** a real OS click (305c's route)
   -- it needs the window focused and a human not touching the mouse, and 600 of them cannot run
   unattended.
2. **The proof that it IS the real path is a negative control, not an argument.**
   `src/client/Weapon/Input.luau` is the only writer of the attribute `DHClaimWhy` in the whole
   repo, inside `Input.fire` itself. Clear it, wait, it stays `nil`; send one click, it comes back
   set. So the click ran the live `Input.fire`.
3. **A RESIDENT, not a per-shot probe.** `execute_luau` has its own module cache, so a probe cannot
   see live module state -- but Instances, attributes and remote connections are shared. The
   resident owns the tracker and the listeners; the host only reads attributes and sends clicks.
   A generation counter retires the previous install, so re-injecting cannot double-count.
4. **The camera is steered only through `Camera.TestLook`** (`DHTestLook`), the camera owner's own
   Studio hook. A probe may not call `Camera.lookAt`: it would aim a fresh copy nobody looks
   through (`tools/studio_mcp.py`, "Staging a scenario").
5. **Every aim point is defined on the DRAWN parts**, once, in one function -- that is the thing the
   five rigs each defined differently.
6. **The self-check cells are appended by the tool**, not by the caller, so a session cannot
   accidentally ship a table nobody checked.

## Measured while building it, 2026-10-28/29, in Karen's Forest Test

Four defects the self-check caught in its own first runs, each fixed and re-measured:

| what the instrument read | cause | fix |
|---|---|---|
| KNOWN-BAD 2/6 where 2 shots were fired | the resident republished its whole row list, so every later cell counted earlier cells' hits | the resident empties its OWN list on a reset counter, not just the attribute |
| `held=nil` on the second cell | the hotbar digit **toggles**; pressing it for the gun already in hand puts it away | press it only while the wrong gun is held |
| `spd=49.7` on a target the server carried at 24 | a one-frame difference on an animated trunk | measure over a 0.15 s window, and publish it so the gate and the row read ONE number |
| the same card dot `(0.975, 0.471)` for every shot | the lead legend is also a `Frame` named `Dot` | skip the one carrying `Lead = true` |

## Note

`ServerStorage.DHLastHits` is **empty for range shots**: the range's card goes out through
`Range.setCardSender` -> `HitLog.sendCard`, which does not write `HitLog`'s trace ring
(`HitLog.recordHit` does). The bench therefore reads zone and impact from the `HitMarker` /
`ShotLanded` remotes the server fired at this client, and prints the ring when it has anything.
