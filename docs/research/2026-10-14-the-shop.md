# The shop in the lodge: buying things with coins (task 178)

2026-10-14. Rule 1 note, written before any code.

## 1. What the system must do

Karen, verbatim:

* 2026-10-13: *"Hunting house where inside can shop things"*.
* 2026-10-10, her design doc: *"There are houses where can buy weapons, License, Gear, Goods"*.
* 2026-10-10: *"Rifle they has to purchase default is double barrel shotgun"*, and
  *"They will have posibility to purchase rifle but has to play a lot it's not few hunts"*.
* 2026-10-10, the weapon ladder, which she accepted with *"yes that seems legit"*:
  shotgun buckshot (default) -> slugs -> open-sight rifle -> scoped rifle.
* 2026-10-10: a beater *"can purchase license to shoot in drive"*.
* 2026-10-10: *"buy packages for outfit"*.

So, as a list of jobs:

1. A player walks up to the counter task 177 left inside the lodge and a panel opens.
2. The panel lists items with PRICES IN COINS, and says of each one whether he owns it, whether it
   is locked behind hunts he has not played, and whether he can afford it.
3. He presses BUY. **The server decides**: it deducts the coins, records the ownership in the saved
   profile, and refuses with a clear line when he is poor, when the item is locked, and when he
   already owns it.
4. What he owns is applied AT THE NEXT DRIVE by the owners that already decide those things -- the
   loadout, the per-drive shell allowance, the fire rules' arming policy, the outfit -- and nothing
   about the drive's own rules changes otherwise.
5. The profile counts COMPLETED HUNTS, because that is the number the unlocks read.

Robux is NOT in this task (the Director's dispatch: "coins only here").

## 2. Sources

### 2.1 ProfileStore 1.0.3 -- MadStudioRoblox, Apache-2.0, maintained (pinned here through Wally)

<https://github.com/MadStudioRoblox/ProfileStore>, API <https://madstudioroblox.github.io/ProfileStore/api/>

Already the save layer of this repository (`src/server/Economy/Store.luau`, task 170). What it says
about a shop: a profile is ONE TABLE for one player, and the game *"update[s] the local copy instead
of sending a data store request for every change"* (Roblox's own best-practice page, which the
library's docs quote). An inventory is therefore not a second store and not a second key -- it is
more fields in `Profile.Data`, written by whoever owns that profile.

* **Good at:** session locking, so two servers cannot both spend the same coins; one writer; no
  retry loop, no backoff and no `UpdateAsync` of ours. A purchase costs nothing on the wire: it is a
  table write, and the library's own auto-save and `EndSession` do the writing.
* **Bad at:** it has no schema migration and no transaction ACROSS profiles (irrelevant here -- a
  purchase touches one player). It also does not reconcile a template on load in any way this repo
  has verified, which is why `Store.read` fills missing keys and keeps unknown ones.

### 2.2 Roblox Creator Docs -- official, maintained

Remote events and callbacks <https://create.roblox.com/docs/scripting/events/remote-events-and-callbacks>,
security tactics <https://create.roblox.com/docs/scripting/security/security-tactics>,
data store best practices <https://create.roblox.com/docs/cloud-services/data-stores/best-practices>

The rule, in their words: *"never trust the client"* -- validate every argument that crosses a
remote, do the arithmetic on the server, and rate-limit the door. The money and the item table live
on the server side of the decision; the client sends an ITEM ID and nothing else, never a price.

* **Good at:** it is the exact shape of the one security question this task asks.
* **Bad at:** no shop example, and nothing about how the catalogue itself should be shaped.

### 2.3 OpenTTD -- GPL-2.0, actively maintained

<https://github.com/OpenTTD/OpenTTD>, `src/command_type.h` (`CommandCost`), `src/command_func.h`
(`DoCommandFlag::Execute`)

Every player action in OpenTTD is a COMMAND that is first run WITHOUT the execute flag: the call
answers a `CommandCost` -- a price, or an error message id -- and only a second, executing call
commits it. Nothing is half-done, and the refusal carries the sentence the UI prints.

* **Good at:** one function answers "may this happen, and what does it cost" before anything is
  written, and the reason is data rather than a thrown error. This repo has adopted it once already
  (`src/server/Weapon/Rules.luau`, task 171).
* **Bad at:** it is a C++ flag-set API over a command table; we want one pure Luau predicate and one
  commit.

### 2.4 ioquake3 -- GPL-2.0, maintained fork of a shipped game

<https://github.com/ioquake/ioq3>, `code/game/bg_misc.c` (`bg_itemlist`), `code/game/g_items.c`
(`Pickup_Weapon`)

Two patterns, both already half-present here. The item table is a STATIC LITERAL array in shared
("bg") code that the server and the client both read -- the shape `Weapons.ROWS` and
`Licences.ROWS` already have, and the reason `Weapons`'s own header gives for refusing a registry.
And picking a weapon up does not copy a weapon: it sets a BIT in a set,
`ps->stats[STAT_WEAPONS] |= 1 << weapon`, which the loadout then reads. Ownership is a set; the
thing owned stays where it was declared.

* **Good at:** ownership as a set read by the loadout, so buying a rifle adds no second rifle and no
  per-player weapon row.
* **Bad at:** its set is per life and never persisted, and it has no prices at all.

### 2.5 What was looked at and NOT taken

* Roblox `MarketplaceService` / `ProcessReceipt` -- that is the Robux path, and the Director's
  dispatch puts Robux later. Its one transferable idea (a purchase must be IDEMPOTENT, because the
  same receipt can arrive twice) is taken: `Shop.refuse` answers `owned` for an item already in the
  set, so a double click cannot be charged twice.
* A generic inventory system with stacks and quantities. Nothing Karen asked for has a quantity: a
  licence, a weapon, an outfit and the slug unlock are each owned or not. A quantity would be a
  mechanism with no caller (CLAUDE.md rule 2).

## 3. The pattern adopted, and why

**A frozen shared catalogue, a pure test-then-execute purchase with a reason string, ownership as a
set in the ONE profile the Economy already owns, behind a server-authoritative rate-limited door.**

1. `ReplicatedStorage.Shop` is the CATALOGUE and the RULES, as frozen data plus pure functions
   (2.4, and `Licences`/`Weapons` here). The panel draws the same prices the server charges, because
   there is one table. No writer, no state, no service.
2. The purchase is `Shop.refuse(...)` then `Economy.purchase(...)` (2.3): the first answers WHICH
   rule says no -- `poor`, `locked`, `owned`, `unknown`, `too-far` -- and the second is the only
   thing that writes, and writes both halves (the coins and the set) in one call that cannot yield.
3. Ownership and the hunt count are FIELDS OF THE PROFILE (2.1), so `Economy` stays the one owner of
   that profile and the shop owns no store, no key and no session.
4. The door is one `RemoteEvent` pair carrying an item ID and nothing else; the server validates the
   id against the catalogue, rate-limits per player, and checks he is actually AT the counter (2.2).

**What is invented, and the written reason rule 2 asks for:** nothing structural. The one local
decision is `Shop.ROWS`' `grants` field, the small map from an item to what it gives (a weapon id,
an ammo kind, a licence, a hat colour), because no source has our weapon ids in it. It is five rows
of data read by functions that already exist (`Weapons.loadoutFor`, `StateMachine.initial`,
`Match.mayCarryWeapon`, `Body.dress`), which is 2.4's "ownership is a set the loadout reads".

## 4. The numeric targets

| Thing | Target | Why |
|---|---|---|
| SLUG AMMO | 120 coins, 0 hunts, permanent | A drive pays ~20-60 coins (`Economy.CONFIG`), so ~3 drives |
| OPEN-SIGHT RIFLE | 600 coins, 10 hunts | the ladder's third rung; **not for sale in this build** (section 5) |
| SCOPED RIFLE | 1500 coins, 25 hunts | *"has to play a lot it's not few hunts"*: ~25-40 drives |
| BEATER LICENCE | 250 coins, 3 hunts | he must have walked a few drives first |
| HAT: RED | 80 coins, 0 hunts | a cosmetic is the cheapest thing in the shop |
| Items in the catalogue | <= 8 | one panel, no scrolling, no paging |
| Purchase round trip | no yield on the server | it runs inside a remote handler, like `onFireRequest` |
| Door rate limit | 4 requests/second/player | `Weapon.Limits`' own order of magnitude |
| Counter reach | 14 studs | the counter is 12 studs wide; a man at either end reaches it |
| Buy button | >= 48 px tall | `Hud.Rail.CONFIG.BUTTON_PX`, over Roblox's 44 px touch minimum |

## 5. What this does NOT do

* No Robux, no `MarketplaceService`, no developer product (the Director's dispatch).
* No selling back, no refunds, no quantities, no trading.
* No second ammo economy: the slug unlock changes the per-drive ALLOWANCE
  (`Weapon.refillForDrive`), it does not add a shell inventory.
* No new weapon. The open-sight rifle's row was taken out by Karen in task 148 (*"please remove
  rifle without scope so we don't implement now"*, archived in
  `backups/2026-10-10-rifle-open-sights.md`), so the catalogue shows that rung and refuses to sell
  it until a build ships the weapon. Selling a thing that grants nothing is the one failure this
  repository would not forgive.
