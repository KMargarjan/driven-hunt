## 1. What the system must do

One drive is one round: two equal teams (drivers push, shooters wait on posts), a 10-minute timer,
six boars released over the drive, individual points for the kill, and then the next drive with the
roles swapped. It must work with **one** player, because that is what the harness runs and what Karen
practises with. Every number is Karen's to retune, and nothing about it may write a boar, a camera, a
weapon state or anything drawn.

Numeric targets are `docs/design/drive.md` §11 and are not repeated here.

## 2. Sources

### A. Roblox `Team`, `Teams` and `Player.Team` — **API confirmed; the design's behavioural claim is not on the page**

<https://create.roblox.com/docs/reference/engine/classes/Team> ·
<https://create.roblox.com/docs/players/teams> · first-party creator docs (creator-docs is CC BY 4.0);
the API ships with the engine · actively maintained. Fetched 2026-09-25.

The page confirms the shape this design needs: teams are `Team` instances in the `Teams` service, a
player is assigned with `player.Team = chosenTeam` (its own sample shows exactly that line), and
`AutoAssignable` is the property that controls automatic assignment (`redTeam.AutoAssignable = true`
in its sample).

**Correction to the design's reading:** the design asserts "`Team.AutoAssignable` defaults to `true`,
so Roblox will assign players itself unless it is turned off" and calls that the most likely way to
build §5.1 wrong. **The page does not state a default.** The mitigation is the same either way and
costs nothing — `Match.Body` sets `AutoAssignable = false` explicitly on both teams when it creates
them — so the build does not depend on knowing the default, and this note does not claim one. What
matters is asserted instead: `match_live.spec` checks both teams exist with `AutoAssignable == false`.

**Good:** one server-authoritative representation of team membership that a client cannot write, that
replicates for free, and that `Boar.CONFIG.isThreat` and `Shotgun.CONFIG.shouldArm` were both written
against.
**Bad:** `Teams` is not a Rojo-owned container, so the two `Team` instances are created at run time
and are invisible to the harness's file comparison — a spec is the only proof they exist.
**Adopted:** two `Team`s created by `Match.Body` at `start()` with `AutoAssignable = false`, compared
by **name** everywhere, never by reference.

### B. Remote events and `Workspace:GetServerTimeNow` — **API confirmed; the synchronisation claim is not on the page**

<https://create.roblox.com/docs/scripting/events/remote-events-and-callbacks> ·
<https://create.roblox.com/docs/reference/engine/classes/Workspace#GetServerTimeNow> · first-party
(CC BY 4.0) · actively maintained. Fetched 2026-09-25.

`GetServerTimeNow(): number` exists and returns a server time. **The page says nothing about how it
synchronises between server and clients** — the design's "a clock both sides agree on" is not
documented there. It is still the right choice (it is the only Roblox clock intended to be shared,
and the alternative — pushing a countdown every second — is 600 broadcasts nobody needs), but the
claim is carried here as a design decision rather than as a documented guarantee, and §15 of the
design already notes that a drift bug cannot appear in a single-process Play session at all.

**Good:** one number per phase instead of a per-second countdown; `FireAllClients` is the right shape
for state every player sees identically; client input is untrusted, which is why this system has no
inbound remote at all.
**Bad:** no rate limiting and no schema validation come with it; a table that is neither a dense
array nor a pure dictionary does not survive the wire (the trap `docs/design/shotgun.md` §2.3 records),
which is why `rows` and `tied` are separate dense arrays.
**Adopted:** two server→client remotes and nothing inbound; the snapshot pushed on change with a
minimum interval and a heartbeat; `phaseEndsAt` as a `GetServerTimeNow` timestamp with the countdown
computed on the client.

### C. `CollectionService` tags — **confirmed**

<https://create.roblox.com/docs/reference/engine/classes/CollectionService> · first-party (CC BY 4.0) ·
actively maintained. Fetched 2026-09-25.

`AddTag(instance, tag)`, `GetTagged(tag) -> Instances` and `GetInstanceAddedSignal(tag)` are all
there with those signatures. The page carries **no** caveats about replication, persistence or name
restrictions — so, as with §B, what the design infers about tags is inference, not documentation.

**Good:** "give me every post" is one call, with no Workspace walk and no naming convention, which is
exactly what lets the Milestone 2 map generator place the markers without this system changing.
**Bad:** a tag is a string with no schema, so a typo yields an empty list and a silently dead rule;
and this repo's harness compares attributes but **not** tags, so a spec is the only proof they are
there.
**Adopted:** five `DrivenHunt.*` tags placed by `TestArena.build`, read into one frozen table by
`Match.Markers`, with a named missing-list and a refusal to start a drive against an incomplete map.
`test_arena.spec` asserts every tag, the count, and the drive line's direction.

### D. Driven-hunt safety practice — recorded, **not used in 1.7a**

Deutscher Jagdverband and equivalent association guidance on *Drückjagd* discipline,
<https://www.jagdverband.de/> · copyrighted web content; facts only, no text and no code · maintained
as public guidance. Not fetched: the safety rule is 1.7b (`SAFETY_ENABLED = false` in this build), so
nothing here depends on it. The design's §8 carries the reasoning for when it lands.

### E. Rodux — named, not adopted, and **the design's status claim is wrong**

<https://github.com/Roblox/rodux> · Apache-2.0 · Roblox's own Redux port. The design says it is
"archived / no longer actively developed". **Checked 2026-09-25: the repository is not archived** —
no archive notice, 136 commits on master and CI workflows configured. The licence is as cited.

The decision is unchanged, and the reasons that survive are the ones that were never about its status:
adopting it would add a Wally package, a `default.project.json` mapping and a Connect click
(`CLAUDE.md`, Toolchain); and its `Store:dispatch` lifecycle would own the phase transitions that
`Phase.step` needs to **return**, so a spec could no longer assert on an effect list. **The pattern is
taken and the package is not**: a pure reducer `(state, event, now, config) -> (state, effects)` is
Redux with the side effects made explicit, which is the part Rodux leaves to middleware.

### F. Inside this repo (rule 2 applies to internal patterns too)

`src/server/Boar/init.luau`: a folder module that owns state and does **nothing on require**, a pure
decision module driven by an injected world and exported for specs, one module that is the only writer
of Instances, every number in one `CONFIG`, `stats()` as the cheap way to assert on a live system, and
`step(dt)` split from `run()` so a spec can drive simulated time. `src/server/Weapon/init.luau`:
injected providers (`setCast`, `setDriveLineProvider`) as the way one owner asks another a question,
a registry that "never knows what a `Player` is", and `forget(player)` as the named lifecycle.
`src/client/Hud/init.luau`: one UI owner that reads published state and is never called by it.
**Adopted whole.** The fourth system either keeps the conventions or starts eroding them.

## 3. The pattern adopted, and what is invented

A pure reducer returning **state plus an explicit effect list** (E's shape without E's package) inside
a folder-module owner with an injected world (F); Roblox's own `Team` as the single representation of
team membership, enforced by the engine (A); tag-based world markers so the map generator can move
everything without this system changing (C); and two outbound remotes carrying a server timestamp
instead of a pushed countdown, with nothing inbound (B).

Invented, with the reason rule 2 requires: **the effect list itself**. Redux and Rodux both leave side
effects to middleware; here they are values the machine returns and the owner performs, because that
is what lets `match_phase.spec` run a whole 600-second drive, with joins, leaves, kills and a hitch,
in milliseconds with no players, no Instances and no clock. The push-credit rule (§7.1) is also this
game's own: no source gives points for driving an animal toward someone else.

## 4. Numeric targets

`docs/design/drive.md` §11 is the single table and this note does not copy it. The one number this
task changes from the design is `MIN_PLAYERS`: **1**, not 2, for Milestone 1 — the Director's decision
F, recorded with its consequences in `reviews/task-32/DESIGN_DELTA.md`.

## 5. What this note could not confirm

- **`Team.AutoAssignable`'s default** (§A) and **`GetServerTimeNow`'s synchronisation guarantee**
  (§B): neither is on the page cited for it. Both are handled by doing the safe thing explicitly and
  asserting what can be asserted.
- **Source D** was not fetched; nothing in 1.7a depends on it.
- Nothing about `LoadCharacter` timing, `PivotTo` on a freshly loaded character, or `Team` assignment
  ordering comes from a source: those are measured in the live spec and in the screenshots, and the
  review request says what was and was not observed.

# Addendum: the safety penalty and the score screen (Milestone 1.7b, Task 35)

Rule 1, for the second half of the same system. Written before the code, on 2026-09-25, in a Builder
session with network access for the source checks. The scope note above said source D was not fetched
because nothing in 1.7a depended on it; **1.7b depends on it, so it was fetched, and §D below is
rewritten with what the page actually says.**

## 1b. What this half must do

A shooter who fires at a driver is punished, comically and visibly: frozen "tied to a tree" until the
drive ends (`TIE_UNTIL_DRIVE_END = true`, Karen's rule as written), announced to everyone in the feed,
and relieved of the gun while tied. At the end of a drive a score screen shows the drive's points, one
row per player, and then the next drive starts with the teams swapped. Karen's numbers: head 100,
chest 80, body 50, legs 30, `PUSH` 25 for the drivers — all already in `Match.CONFIG` since 1.7a, and
unchanged here. `SAFETY_ENABLED` and `SCOREBOARD_ENABLED` go from `false` to `true`.

## 2b. Sources

### D. Driven-hunt safety practice — **fetched this time, and it settles the rule's shape**

<https://www.jagdverband.de/content/sicherheit-vor-jagderfolg> — Deutscher Jagdverband e.V. (DJV),
published 2016-10-14 · copyrighted web content, facts only, no text and no code copied · maintained as
the association's public safety guidance. What it actually says, checked 2026-09-25:

- "In Richtung von Mitjägern und Hunden zu schießen ist untersagt" — shooting **in the direction of
  fellow hunters and dogs** is forbidden. This is the rule the design picked, and the page states it
  as a direction-at-a-person rule, not as a fixed cone.
- "Ein Schuss in Richtung von Personen, Autos und Siedlungen ist strengstens untersagt."
- The **neighbour** rule is separate and is a number: "Der Schusswinkel zum Nachbarn muss größer als
  30 Grad sein" — the angle to the next stand must exceed 30°.
- The shooter must know what is behind the target before aiming.

Corroborating association and trade guidance, read for the *Drückjagd* case specifically (never shoot
into the drive line; never take that shot once you can see beaters; the field of fire is agreed before
the drive starts): <https://ljv-hessen.de/welche-haftungsrisiken-bergen-bewegungsjagden/> (Landesjagd-
verband Hessen) and <https://www.pirsch.de/jagdpraxis/jagdarten/drueckjagd-so-solltet-ihr-euch-auf-dem-stand-verhalten-40062>
(PIRSCH, trade magazine). Both are copyrighted web content, facts only.

**What is adopted, and what this changes about the design.** The design's v1 rule — *you fired at a
driver*, judged from the shot's own path and the drivers' positions — is what the DJV page states,
and the design's rejection of "any shot within 45° of the drivers" as the *verdict* is right for the
same reason: a shooter on a post faces the drive, so a cone alone forbids every legitimate shot. The
45° arc stays where the design put it, as the weapon's cheap **filter**.

**The one thing the sources add that the design did not have:** the neighbour rule is the *other* real
rule and it comes with a number, 30°. `docs/design/drive.md` §8.1 already names it as the obvious v1.1
addition; the source confirms the angle. Not built here (it is a second rule, not this task), queued
in `TASKS.md`.

### G. Roblox `Humanoid.WalkSpeed`, `BasePart.Anchored` — how a player is actually frozen

<https://create.roblox.com/docs/reference/engine/classes/Humanoid#WalkSpeed> ·
<https://create.roblox.com/docs/reference/engine/classes/BasePart#Anchored> · Roblox's own reference,
maintained. `WalkSpeed = 0` is the ordinary way to stop a character, and the stock `PlayerModule`
drives movement through `Humanoid:Move` and never writes `WalkSpeed`, so this adds no second writer —
the same boundary `docs/design/camera.md` §6.3 records for the camera.

**What neither page states, and what follows from it:** a player's character is simulated by *their
own client*, so a server-side `PivotTo` alone is a suggestion the client can immediately walk out of.
That is why `Anchored` is in the design at all ("the belt to `WalkSpeed`'s braces") — and it is why
this build sets `Anchored` **before** the pivot rather than after it, which is the design's list order.
Not confirmed from a page: measured behaviour is what a two-player run is for, and the request says so.

### H. Inside this repo (rule 2 again)

- `Hud.onHitMarker` (Task 28) is a named public function "so a client spec can drive exactly the code
  path the wire drives". `Hud.renderScore` and `Hud.renderTied` are the same shape for the same reason,
  and here the reason is forced: a drive is 600 s, so **no harness run ever reaches the `Scoring`
  phase**, and without that seam the design's own visibility assertion (§12.7 item 4) could not be
  written at all.
- `Weapon.setArmingPolicy` / `refreshArming` (Task 32) already exist: a tie is just a third answer
  from the policy the weapon already asks, so nothing about arming is new.
- `Boar.Body` / `Match.Body`: the module that touches Instances so nothing else has to. The rope and
  the freeze go there, and `Body.tieCharacter` takes a `Model` rather than a `Player` so a spec can
  drive it against a rig of its own instead of against the one real player in a Play session.

## 3b. What is invented rather than borrowed (rule 2)

**Nothing in the rule's shape.** The one piece with no source is the *comedy*: real hunting practice
takes a licence away, and "tied to a tree until the drive ends, with a rope you can see across the
arena" is Karen's design decision, recorded in `reviews/task-29/BRIEF.md`.

`SAFETY_BODY_STUDS` is this build's own and is a **correction to the design**, not an invention of a
rule: see `reviews/task-35/DESIGN_DELTA.md`.

## 4b. Numeric targets

`docs/design/drive.md` §11.4 is the table. Three numbers differ from it and each is in the delta file:
`TIE_GAP_STUDS = 2.5` replaces `TIE_OFFSET = CFrame.new(0, 0, 2.5)`, `SAFETY_BODY_STUDS = 4` is new,
and `ROPE_COLOR` is `RGB(170, 130, 85)` rather than `RGB(120, 90, 60)` — the design itself said to
check it on screen, because two colours in this repo have already read near-black on first try.

## 5b. What this addendum could not confirm

- The DJV page gives no distance for "in the direction of": `SAFETY_MISS_STUDS = 12` (~3.4 m) is
  Karen's feel number, marked K, and nothing in the sources fixes it.

# Addendum 2: sounders — a group of boars that moves as one (Task 60, the design's 57a)

Written **before** the code (rule 1). `docs/design/drive.md` §6.6–§6.9, §11.7 and §16 G/H/I are the
design; this note is the Builder's own reading of the sources it names, and it records where the
pages say something different from the design.

## 1c. What this half must do

Karen: boars arrive as a **mix of singles and groups of 2–5**, as in her reference — a sounder
crossing a forest road in front of the line. Task 60 builds only the half that makes a sounder
**exist and behave**: `Runtime:spawnSounder`, the group bookkeeping, and the follower's steering.
The drive releasing sounders is the next task (Director decision J).

## 2c. Sources, fetched 2026-09-26

### G. Craig Reynolds, *Steering Behaviors For Autonomous Characters* (GDC 1999)
<https://www.red3d.com/cwr/steer/gdc99/> · the page carries **no copyright or licence notice**;
technique taken, **no code** · last updated **3 May 1999** — frozen, and still the standard reference.
This repo already cites it for wander, flee and the probe turn (`src/server/Boar/Brain.luau`).
**Good:** it defines the exact behaviours this task needs and names them as the code will —
*leader following* ("the arrival target is a point offset slightly behind the leader"), and the
follower-in-front rule ("it will steer laterally away from the leader's path before resuming
**arrival** behavior"). It gives separation as "a repulsive force … normalizing, and then applying a
1/r weighting", cohesion toward the "average position", alignment toward the average velocity. On
combining: "compute each of the component steering behaviors and sum them together, possibly with a
weighting factor for each", with prioritisation named as the alternative.
**Bad:** no map knowledge, so pure steering walks a follower into a dead end behind a hedge; it says
nothing about a leader dying; the weights are not in the paper.
**Adopted:** leader following as the formation rule on top of the leader's navmesh route, the
weighted sum, and the strict steering/locomotion split this Brain already has (`slew` + `ACCEL`
limit the setpoint, never the physics).
**Adopted with a change:** separation here is `(SEPARATION_STUDS / max(d, 1)) − 1`, clamped at 0 —
the same 1/r shape, but zero beyond `SEPARATION_STUDS` so a neighbour 20 studs away contributes
nothing at all. The paper's plain 1/r never reaches zero.

### H. Craig Reynolds, *Boids* (the 1987 model's page)
<https://www.red3d.com/cwr/boids/> · **no copyright or licence notice** on the page; technique taken,
no code · last updated **6 September 2001**, the work dated from **1986**.
**Good:** the origin of the three rules, in the words the code uses — separation "steer to avoid
crowding local flockmates", alignment "steer towards the average heading of local flockmates",
cohesion "steer to move toward the average position of local flockmates". *Local* flockmates is where
`NEIGHBOUR_STUDS` comes from, and why the cost is O(n²) over n ≤ 5 rather than over the field.
**Bad:** a leaderless flock in open space with no ground and no goal — it has nothing to say about a
herd being driven toward a line.
**A CORRECTION TO THE DESIGN.** `drive.md` §16 H says this page "makes the point this design leans on
hardest: **the rules must be prioritised, with collision avoidance winning**". **It does not.** The
page states no hierarchy among the three rules; the only priority it names is that obstacle avoidance
was added later and goal-seeking is "a low priority" behaviour. The prioritisation idea is on the
**GDC 1999** page (source G), and even there it is offered as an alternative to the weighted sum. So
`SEPARATION = 1.6 > COHESION = 1.0` is **this build's decision with this repo's own reason** — five
`CanCollide` bodies of 23 mass driven at `MAX_FORCE = 6000` interpenetrating is a physics fight, not
a graphical artefact — and it is not a claim about what Reynolds wrote. Recorded rather than quietly
inherited (rule 8).

### I. OpenSteer — named, **not adopted**
<https://opensteer.sourceforge.net/> · MIT · **unmaintained** (dormant since the mid-2000s).
Canonical C++ implementation of exactly this decomposition; vendoring or porting it would be the
"invented foundation" failure with a licence attached. Same call `docs/design/boar-ai.md` §8 made
about SimplePath. **Pattern confirmed, code not taken.**

### J. Inside this repo (rule 2)
`src/server/Boar/Brain.luau`: the Observation → Intent contract is what makes a formation testable
with no physics — the sounder arrives as `obs.sounder`, plain values only, and the Brain holds no
reference to another boar. `src/server/Boar/init.luau`: the Runtime is already the only writer of
boar state, so the sounder records live there and nowhere else.

## 3c. Numeric targets

`docs/design/drive.md` §11.7's `Boar.CONFIG.SOUNDER` table is the source; it is copied into

## 4c. What this addendum could not confirm

- **Nothing in either page is dated later than 2001**, so "still the standard reference" is a
  judgement, not a fact off the page.
- The pages carry **no licence notice at all**, which is not the same as permissive. Only the
  technique is taken; no text longer than the phrases quoted above and no code.
- Whether five colliding bodies at `MAX_FORCE = 6000` actually behave is a **physics** question no
  paper answers: the live spec's `UpVector.Y > 0.9` assertion and the screenshots are the evidence.
