# Bots fill the drive: visible NPC beaters and hunters

Task 161. Rule 1 note, written before any code.

## 1. What the system must do

Karen's words, 2026-10-11 (her v1 rule): *"Let's make 4 hunters 4 beaters"*. The Director's
proposal she answered **"start now"** to: *"Real visible bots: beaters walking in orange vests,
hunters standing on stands... a solo player still feels part of a full drive; at launch servers will
often have only 1-3 players, and bots fill the 4+4 so the game still works."*

Karen tests **solo**, in the Forest Test. So the thing being built is the drive she sees when she is
the only person in it.

1. **Fill.** A drive wants 4 hunters and 4 beaters. Every slot a real player does not fill is
   filled by a bot, per side, and a bot gives the slot back when a real player takes it.
2. **Bot beaters** are R15 rigs in the beater outfit, on the beaters' start line, **held through the
   countdown exactly as a player is** (task 158), then walking to the road in a line at beater pace,
   blowing the horn now and then, and **spooking boars through the same door a real beater's walk
   goes through** (tasks 153/154) -- not a second push mechanism.
3. **Bot hunters** are R15 rigs in the hunter outfit on the stands no real hunter has, standing and
   facing the drive. **They do not shoot.** A shooting bot is its own task (TASKS.md 161a).
4. **A bot is not a player.** No score row, no DataStore, no team membership, no `participants`
   entry, no Player object, nothing a safety penalty can be judged against.
5. **A switch turns the whole thing off** and leaves today's behaviour bit for bit.
6. **Removed and re-placed every drive**, so a roster that changed between drives cannot leave a bot
   standing on a stand a real hunter now owns.

## 2. The sources

### 2.1 ioquake3, `code/game/g_bot.c` -- `G_CheckMinimumPlayers`

<https://github.com/ioquake/ioq3/blob/main/code/game/g_bot.c> -- **GPL-2.0**, actively maintained
(`ioquake/ioq3`, commits through 2026). **This project already borrows from this repository**
(tasks 159 and 160 both quote `g_team.h` and `g_main.c`), so it is prior art we have read before.

Fetched 2026-10-12. The function, verbatim:

```c
void G_CheckMinimumPlayers( void ) {
	int minplayers;
	int humanplayers, botplayers;
	static int checkminimumplayers_time;

	if (level.intermissiontime) return;
	//only check once each 10 seconds
	if (checkminimumplayers_time > level.time - 10000) {
		return;
	}
	checkminimumplayers_time = level.time;
	trap_Cvar_Update(&bot_minplayers);
	minplayers = bot_minplayers.integer;
	if (minplayers <= 0) return;

	if (g_gametype.integer >= GT_TEAM) {
		if (minplayers >= g_maxclients.integer / 2) {
			minplayers = (g_maxclients.integer / 2) -1;
		}

		humanplayers = G_CountHumanPlayers( TEAM_RED );
		botplayers = G_CountBotPlayers(	TEAM_RED );
		//
		if (humanplayers + botplayers < minplayers) {
			G_AddRandomBot( TEAM_RED );
		} else if (humanplayers + botplayers > minplayers && botplayers) {
			G_RemoveRandomBot( TEAM_RED );
		}
```

**What it does well.** It is the whole design, already written by somebody else, and it is twenty
years old in a shipped game:

* the target is **per team**, not per server -- `TEAM_RED` and `TEAM_BLUE` are counted and filled
  separately, which is Karen's "4 hunters 4 beaters" and not "8 bodies";
* the count is **humans + bots against the target**, so the arithmetic is one subtraction and a bot
  is pushed out the moment a human takes the slot (`> minplayers && botplayers` removes one);
* `minplayers <= 0` **turns the whole thing off** -- the switch is the target itself, not a second
  boolean beside it;
* it refuses to run **during the intermission** (`level.intermissiontime`), because a roster that is
  about to be rebuilt is not a roster worth filling;
* the cap (`minplayers >= g_maxclients/2`) keeps a slot free for a human who is still connecting.

**What it does badly, for us.** Its bots are **clients**. `G_AddRandomBot` goes through
`ClientBegin`, so a Quake bot has a client number, a name, a score and a rank, and it appears in the
scoreboard beside the humans. That is the one thing Karen's bots must not do: this game's board is
the results table she reads at the end of every drive, and a bot in it would be a fake player with
fake points. And its clock is a **10-second timer**, which is a poll; our drive already has the
boundary that matters (`Match.PhaseChanged`), so a timer here would be a second answer to "when is
the roster settled".

**Adopted:** the per-team fill arithmetic, the add-and-remove symmetry, the "target 0 is off" switch
and the "not during the intermission" guard -- re-pointed at the drive's own phase boundary and at
rigs that are not clients.

### 2.2 Roblox, "Improve performance"

<https://create.roblox.com/docs/performance-optimization/improve> -- Roblox's own documentation,
current (fetched 2026-10-12). The vendor's cost statement for exactly this feature:

> "Humanoid is a class that provides a wide range of functionalities to player and non player
> characters (NPCs). Although powerful, a Humanoid comes with a significant computation cost."

> "There is a performance cost to leaving certain HumanoidStateTypes enabled."

> "Static NPCs that do not move generally have no need for the Humanoid class."

> "NPC animations that run on the server need to be simulated on the server and replicated to the
> client."

> "Pool NPC models with frequent respawning."

**What it does well.** It splits our two bot kinds for us. A bot **beater** walks, so it needs the
Humanoid and its state machine. A bot **hunter** stands on a post and never moves -- the vendor's
own sentence says such an NPC has no need for the class at all, and the furthest we can take that
while still wearing the outfit (`Humanoid:AddAccessory` needs a Humanoid) is: anchored root, state
machine off, every state disabled, no animation played from the server.

**What it does badly.** **It contains no numbers.** There is nothing here that says eight humanoids
is cheap or four hundred is dear, so "8 bots are fine" is not a claim this source can support. The
only honest version of that claim is a measurement, which is why the bot step prints its own cost
per drive (section 5) rather than being asserted to be small.

Its last line, pooling, is **rejected for now and said out loud**: the warning is about *frequent*
respawning, and this system builds eight rigs once per ten-minute drive. A pool would be live state
carried across a drive boundary, which is the thing section 1 item 6 exists to prevent. If a
measurement ever asks for it, the pool goes in with that measurement beside it (TASKS.md 161a).

### 2.3 Roblox, "Character pathfinding" + the `Humanoid:MoveTo` reference

<https://create.roblox.com/docs/characters/pathfinding> and
<https://create.roblox.com/docs/reference/engine/classes/Humanoid#MoveTo> -- vendor docs, current
(fetched 2026-10-12).

The guide's loop:

> "After you've created a valid path with CreatePath(), it must be computed by calling
> Path:ComputeAsync() with a Vector3 for both the starting point and destination."

> "Once the Path is computed, it will contain a series of waypoints that trace the path from start to
> end."

> "To handle this, you can connect the Path.Blocked event and re-compute the path around whatever
> blocked it" -- and "the path is re-computed only if the blocked waypoint is ahead of the current
> waypoint."

And the one fact that decides the shape of our walk loop, from the `MoveTo` reference and its own
code sample: **`MoveTo` times out after 8 seconds** -- if the goal is not reached within 8 seconds
the humanoid stops walking and `MoveToFinished` fires with `reached = false`; the timeout is reset by
calling `MoveTo` again inside the window, which is what the official sample does.

**What it does well.** It is the engine's own answer and it costs us nothing to obey: a beater has
some 240 studs of wood to cross at a walk, which is half a minute, so **one `MoveTo` cannot do it**
and the loop has to re-issue regardless of which route it follows. That timeout is a number, not an
opinion, and it sets our re-issue interval.

**What it does badly, for us.** The pathfinding half is written for **one agent chasing one target**.
It says nothing about a LINE of agents walking abreast, which is the only thing a beater line is --
and a shortest path around trunks is exactly what breaks a line, because each agent's detour is its
own. It also costs a `ComputeAsync` per bot per retarget, with no documented throttle or limit (both
pages are silent on cost), so the price of eight agents recomputing is unknown and unmeasurable from
the documentation.

**Adopted:** the per-waypoint `MoveTo` loop and the 8-second re-issue. **Rejected:**
`PathfindingService` -- see section 3.

### 2.4 SimplePath, `ahmicy/simplepath`

<https://github.com/ahmicy/simplepath> -- **MIT**, 70 stars, created 2021-04-29, **last pushed
2026-06-12**, not archived. `src/SimplePath.lua`, 349 lines, read 2026-10-12. The community's
standard wrapper round the guide above, and the reason to read it is that it has already found the
loop's sharp edges:

* a **`MoveToFinished` chain** that advances the waypoint index and re-issues
  (`self._humanoid:MoveTo(self._waypoints[self._currentWaypoint].Position)`), rather than a `wait`
  per leg;
* a **`Path.Blocked`** handler that fires only for a waypoint ahead of the agent;
* **`TIME_VARIANCE = 0.07`** -- a floor on how often a recompute may happen at all:
  `if os.clock() - self._t <= self._settings.TIME_VARIANCE ... then return`. A throttle on the
  expensive call, declared as data.

**What it does well.** It proves the shape, and it proves that the expensive operation needs a
declared floor. Its licence is compatible and its maintenance is live.

**What it does badly, for us.** It is a **pathfinding** module, and section 3 rejects pathfinding for
the beater line -- adopting it would mean adopting the per-agent `ComputeAsync` we are avoiding. It
is also one object per agent with its own connections and its own clock, where this system wants one
stepper over all eight bots (one Heartbeat, not eight).

**Adopted:** the idea that the expensive operation gets a declared minimum interval. **Not
adopted:** the module. It stays the named escape hatch if the straight walk is ever measured getting
stuck (TASKS.md 161a).

### 2.5 In-repo prior art (rule 2 points here first)

`ForestTest.computeRoute` / `ForestTest.clearRoute` (task 127) already solve "walk from A to B
through this wood without hanging on a trunk" for the animals, with `ForestTest.nearestSolid` and
`ForestTest.roomToStand` as the trunk measurements and `Boar.CONFIG.MOVE`'s speed-scaled whisker as
the side-step. `Match.Body` already owns what a character wears and where it stands, and
`Body.dress(character, team, config)` takes a **Model**, not a Player -- so a rig can be dressed by
the one owner of dressing with no change to it at all. These are reviewed, in this repo, and
measured against this very terrain.

## 3. The pattern adopted, and why

**FILL -- ioquake3's `G_CheckMinimumPlayers`, re-pointed.** One pure function:
`Bots.fillCounts(realPerTeam, config)` returning how many hunters and how many beaters to build,
which is `max(0, target - real)` per side with the total capped. Called at the drive's own boundary
(entering `Assigning`), never on a timer. Target 0 is the switch, as `bot_minplayers <= 0` is.

**WALK -- `Humanoid:MoveTo` re-issued, NOT `PathfindingService`.** Three reasons, in order:

1. **The line is the feature.** Karen's beaters walk abreast toward the road (*"beater are behind
   animals and moving towards hunter line (road) like in real life"*, 2026-10-11). A shortest path
   is per agent, so eight shortest paths are eight different detours and the line is gone. A lane
   per bot -- its own X on the start line, its own point on the road -- IS the line, and `MoveTo`
   down a lane keeps it.
2. **The cost is unknown and the alternative's is zero.** Neither vendor page states a limit, a
   yield cost or a throttle for `ComputeAsync`; SimplePath's `TIME_VARIANCE` exists because the
   community found it needed one. `MoveTo` toward a lane point costs one property write.
3. **The obstacle case is already solved in this repo** (2.5) and is *smaller* for a person than for
   an animal: a beater who clips a trunk needs to step round one trunk, not re-plan. So the handling
   is the repo's own whisker -- a short ray down the lane, and if it hits, aim at the cleared side
   for a few seconds -- and nothing more.

   **If that is ever measured failing** (a bot that has not moved for `STUCK_SECONDS`), the escape
   hatch is section 2.4's module, and the stuck count is printed every drive so the question is
   answered by a number. `ForestTest`'s own `stuck` counter is the precedent.

**STAND -- no humanoid work at all.** The vendor's "static NPCs ... have no need for the Humanoid
class" taken as far as the outfit allows: root anchored on the post, `EvaluateStateMachine = false`,
every `HumanoidStateType` disabled, nothing animated from the server, `DisplayDistanceType` set to
`None` so eight name tags do not render.

**ONE PUSH SOURCE.** A bot beater is a BODY standing in the wood, so it goes into the lists the real
beaters go into -- `ForestTest.realBeaters()`, where "real" has always meant *as against a phantom*
-- and into the world's threat list as `kind = "driver"` with **no `phantom` mark**, because
somebody IS standing there. **The phantoms:** the Forest Test's wave mode invents a phantom beater
11 studs behind each herd (`ForestTest.boarThreats`); with bots on they are **suppressed**, so the
push comes from the bodies Karen can see and not from both at once. The LINE mode never had any
(TASKS.md 153b), so nothing there changes.

**A BOT IS NOT A PLAYER, and the mechanism is that it has no userId.** Every door in this drive is
already keyed by userId and already refuses a non-numeric one -- `Match.playerDrivers` filters the
quick test's phantom and the forest's wave beaters out by exactly that, `Match.pushCreditable`
refuses an absent userId, and `Phase.participantIds` reads `state.participants`, which only a Player
is ever written into. So "no score row" is **structural**, not a filter somebody has to remember.

**THE DRIVE ENDS WHEN THE LINE IS THROUGH, bots included.** Karen: *"Timer or when all beaters cross
line of hunters"*. Today `Match.beaterCrossing` counts real beaters only, and TASKS.md 159a(f) is
her open complaint about what that means solo: **one beater, one crossing, the drive is over**. With
bots on, the line is real beaters + bot beaters, so a solo beater crossing first ends nothing and
the drive ends when the last of the line is past -- which is her sentence read literally and the
honest reading of "all beaters". The counting stays in the owner and the RULE stays
`Phase.beatersThrough`, which only compares two numbers.

**THE RESULTS SCENE INCLUDES THEM** (the dispatch's "nice"): `Scene.ringLayout` already takes a
count, so the ring is `#participants + #bots` wide and the bots take the slots after the players.
It costs one argument and it is what Karen described -- *"all they standing around the animals"* --
with a ring of people in it instead of one person.

**THE RIG COMES FROM AN INJECTED SOURCE.** `Players:CreateHumanoidModelFromDescription(desc,
Enum.HumanoidRigType.R15)` is the engine's own R15 builder and is the default; the source is a
settable seam (`Bots.setRigSource`), which is the shape `Boar.setModelSource` and
`Body.setAccessorySource` already have -- so every spec builds bots out of a fake rig with no avatar
service, no web call and no Play.

## 4. What is NOT in this task, and is named so it is declared rather than discovered

* **A bot does not shoot.** No weapon, no aim, no safety arc, no kill, no points. TASKS.md 161a.
* **A bot cannot be endangered by a shot.** It is not a driver the safety rule can protect (no
  userId, so `Match.playerDrivers` drops it), so firing through a bot beater is not yet a penalty.
  That is a real gap in Karen's safety rule the moment bots are visible, and the fix is a design
  decision -- should a fake beater be able to tie a real hunter to a tree? -- so it is hers:
  TASKS.md 161a.
* **No dogs, no names, no chat, no animation beyond the engine's own walk.**

## 5. The numeric targets

| Number | Value | Why |
|---|---|---|
| `TARGET.hunters` | 4 | Karen, 2026-10-11: *"Let's make 4 hunters 4 beaters"* |
| `TARGET.beaters` | 4 | the same sentence |
| `MAX_BOTS` | 8 | the two targets summed: a cap that cannot be exceeded whatever the targets say |
| `ENABLED` | the switch | `TARGET.* = 0` is off per side; `ENABLED = false` is off whole, and off means today's behaviour exactly |
| beater `WALK_SPEED` | 9 studs/s | a walk, not a jog. A player's default is 16 (`Body.defaultWalkSpeed`), which reads as a man in a hurry; a beater walks the wood. Karen's eye decides and it is one line |
| `MOVE_REISSUE_SECONDS` | 2 | well inside the engine's documented 8-second `MoveTo` timeout (2.3), so a 30-second walk never stalls |
| `STEP_HZ` | 5 | the bot stepper's own clock. The drive's is 4 (`MATCH_STEP_HZ`) and the boar runtime has its own; this is a third, and it is declared |
| `LANE_SPACING_STUDS` | 18 | the beaters stand abreast and stay abreast: wide enough to read as a line from a stand 200 studs away, tight enough that four of them cover one crossing |
| horn `EVERY_SECONDS` | 18 to 35, jittered | *"blow the horn now and then"*. The floor is the real `Horn.CONFIG.COOLDOWN` (1.5 s) and this rhythm is far above it, so a bot can never be the thing that tests the cooldown |
| horn reach | `Horn.spookStuds(Horn.CONFIG)` | the REAL reach, read from the horn's own data. No second number |
| `STUCK_SECONDS` | 4 | a bot that has not moved `STUCK_STUDS` in this long is stuck: it side-steps, and the count is printed |
| `STUCK_STUDS` | 3 | at 9 studs/s, four seconds of walking is 36 studs; 3 is unambiguously "not walking" |
| the bot step's own cost | printed, not asserted | section 2.2 has no numbers, so this one is MEASURED: the stepper times itself and the console says how long the bots cost per step. Karen's rule: no frames hunting -- one line of numbers, not a trace |

## 6. Owner

One writer per thing, and the two that already exist do not move:

| Thing | Owner |
|---|---|
| the bot rigs: their Instances, their lifetime, their movement, their horn rhythm | **`Bots`** (new) |
| what a bot WEARS | **`Match.Body`**, unchanged -- `Body.dress(rig, team, config)` |
| where a bot STANDS at the start, and in the results ring | **`Bots`**, off geometry the drive hands it (`world.placement` / `Scene.ringLayout`) -- it never reads the markers itself |
| how many bots there are | **`Bots.fillCounts`**, pure, called by the drive at its own boundary |
| whether a drive has ended | **`Phase.beatersThrough`**, unchanged -- the owner just counts bot beaters into the two numbers it already measures |
| what a boar can perceive | the world's threat list, unchanged -- a bot is one more entry in it |

`Bots` is injected into `Match.start` as `world.bots`, because **no owner requires another owner**
(the rule `ForestTestBoot` and `MatchBoot` are both written to). A world that injects nothing gets
today's drive, with no bots and no new code path -- which is the switch's second half.
