# The map: a full map on M and a round minimap in the corner

2026-10-11 · Task 155 · Builder

## What Karen asked for

Verbatim, 2026-10-11 ~14:10, after her first beater playtest:

> "I am missing map, we need a map when click M where will be hunter position where they stand and
> what direction to move also can see other players on map moving / and small map in left or right
> corner circle like is on another games hwere showing where to move ect"

Read literally, that is six requirements and one shape:

1. **M opens a map.** A key, a toggle.
2. **Where the hunters stand** — the stand positions, as places on the map.
3. **What direction to move** — the push direction. She is a beater; the thing she cannot work out
   on the ground is which way the road is, which is the same sentence that produced the compass in
   task 125 (*"we need to indicate from what side drive is comming"*), one axis short.
4. **Other players moving** — live markers, not a static plan.
5. **A small round map in a corner**, "like is on another games".
6. **Mobile** is in v1 (`docs/PROJECT_CONTEXT.md` build order 4 plus the Director's dispatch), so
   the map must open without a keyboard.

## What the system must do

- Draw, from inside the client, a top-down picture of the drive area: the **road** (the hunters'
  line), **each stand**, the **push direction**, and **every player** as a live marker, coloured by
  team, with the local player's own marker distinct.
- Two sizes of the same picture: a **full map** (toggled) and a **round minimap** (always on),
  centred on the player.
- Work in **two worlds that do not share a map**: the Forest Test (a bought terrain with a sine
  road, `src/shared/ForestTest/init.luau`) and the DEV Match world (`src/shared/Map` +
  `MapGen`, tagged markers, a straight road at `Map.ROAD.z`).
- Cost nothing a phone cannot pay, and **never cover** the compass (y 76..102), the drive bar
  (y 8..34), the tied banner (44..68) or the ammo readout.
- Be ONE writer (rule 3). Everything drawn in this game is `PlayerScripts.Hud`'s
  (`src/client/Hud/init.luau` header), and nothing here changes that.

### Numeric targets

| Target | Value | Why |
|---|---|---|
| Minimap diameter | 150 px | Readable at 1080p and at a phone's ~400 px width without eating a quarter of it |
| Minimap range | 300 studs radius | 84 m at `0.28` m/stud: two stand spacings (`STAND_SPACING` 150), so a beater sees the road and at least two stands before she reaches them |
| Full map coverage | the whole drive area | Forest Test: `CENTRE.X ± HALF_SPAN` (1,600 studs) by the beater start to past `EXIT_Z` (~1,100 studs) |
| Redraw rate | ≤ 20 Hz for markers | A marker is a position, and a walking player moves 16 studs/s = 0.8 studs per tick: under one pixel on the minimap. The compass redraws per frame because it tracks the *view*; a map tracks *positions* |
| Static geometry | built once | The road and the stands never move inside a session; only markers move |
| Player markers | ≤ 16 | `docs/PROJECT_CONTEXT.md`: 10-16 players |
| Frame budget | ≤ 1 ms/tick on the client | Everything is `Frame.Position` writes; no clone, no raycast, no `GetPartBoundsInRadius` |

## Three ways to build it, and what each does well and badly

### A. ViewportFrame with a top-down camera

A `ViewportFrame` renders 3D objects through its own camera into a 2D rectangle.

- **Official docs** — [`ViewportFrame` / Viewport frames](https://create.roblox.com/docs/ui/viewport-frames),
  source at [Roblox/creator-docs](https://github.com/Roblox/creator-docs/blob/main/content/en-us/ui/viewport-frames.md).
  **Licence: CC BY 4.0 for prose, MIT for code samples** (`LICENSE` / `LICENSE-CODE`).
  **Maintenance: active** (2,173 commits on main, open PRs). The doc names this use case first:
  *"A minimap of your game directly in the corner of a user's screen"*, and *"when you want to
  update the view of your ViewportFrame, be sure to update the camera, not the objects within the
  view"*.
- **The community tutorial that actually built it** —
  [Creating An Efficient\* Viewport Minimap](https://devforum.roblox.com/t/creating-an-efficient-viewport-minimap/1179030),
  devforum, 2021-04-20. **Licence: devforum post, no grant — readable, not copyable.**
  **Maintenance: a 2021 post, not a module.** Region3 culling, clone the nearby parts into the
  viewport **every frame**, move the camera overhead, rotate an arrow for the player. Tested on
  17,315 parts (734 in a heavy region) with *"extremely minor spikes"*.

**Does well:** it is the real world, so it can never disagree with the world. No second description
of the map to keep in step. Handles a procedurally generated map that changes at runtime — which is
the author's own stated reason for choosing it.

**Does badly, and this is what rules it out here:**

1. **It cannot draw our ground at all.** Terrain is not renderable inside a ViewportFrame: *"You
   can't put Terrain instances under ViewportFrame, in which objects have to be parented under it
   to render"* — a six-year-old open feature request,
   [Add terrain support for ViewportFrame](https://devforum.roblox.com/t/add-terrain-support-rendering-from-outside-its-parental-structure-for-viewportframe/219346),
   still open, with [Rendering terrain in a viewportframe](https://devforum.roblox.com/t/rendering-terrain-in-a-viewportframe/1931034)
   saying the same. **The Forest Test's ground IS terrain** (a bought terrain the Director built the
   road into) and so is the DEV map's (`MapGen.Ground` paints Terrain materials). A top-down
   viewport of this world would be 831 floating tree meshes over a transparent void — the exact
   failure `docs/PROJECT_CONTEXT.md` records twice ("a visibility audit certified a blank screen").
2. **The author's own asterisk.** Efficient *"relative to other viewport-based systems"*; he states
   plainly that image-based solutions substantially outperform it, and that per-frame cloning and
   Region3 do not scale.
3. **Mobile.** The render target is hard-capped at 1024x1024 and rendering the workspace a second
   time costs frame rate ([ViewportFrame Upgrades](https://devforum.roblox.com/t/viewportframe-upgrades/3953219),
   [Are ViewportFrames more/less efficient than images?](https://devforum.roblox.com/t/are-viewportframes-moreless-efficient-than-images/254323)).
   Karen wants mobile in v1 and this world already carries 831 trees plus up to 60 boars.

### B. A pre-rendered map image

Render the place once, offline, into an image; show a window of it and move it under the player.

- **RoRender V4** — [devforum](https://devforum.roblox.com/t/rorender-v4-minimap-generator/3525559),
  2025-03-04, raytraced cloud renderer with a Photoshop-like editor, images capped at 7k x 7k.
  **Licence: the in-Studio render plugin is open source; the web editor is paid** (credits or
  subscription). **Maintenance: active**, a ground-up V4 rebuild.
- **Minimap Render & Gui**, Etheroit and RainyLofi —
  [devforum](https://devforum.roblox.com/t/minimap-render-gui/1995940), 2022-09-25, code at
  [dv8-studio/renderer](https://github.com/dv8-studio/renderer). Splits the map into a grid of
  pre-rendered image chunks and ships a GUI that shows them. **Licence: not stated in the post or
  on the repo — so "readable, not copyable".** **Maintenance: 2022, no activity since.** Its blip
  rule is the one worth stealing: markers are coloured by team and an out-of-range one is *"pinned
  (will stick on the border instead of disappearing when they're out of bounds)"*.

**Does well:** cheapest thing at runtime — one `ImageLabel` and a `Position` write. Looks like a
real map, because it is a picture of one. This is what shipped games do.

**Does badly:**

1. **It goes stale silently.** The Director moves the road or adds a stand, nobody re-renders, and
   the map now lies — with no test that can see it. Our two worlds are both *under construction*
   this month (`TASKS.md`: the map is the next roadmap block).
2. **An image is a Roblox asset id**, which means an upload, Karen's OK, a row in
   `assets/uploads.json`, and moderation — per world, per change.
3. **Paid or unmaintained.** RoRender's editor is a subscription; the free alternative has not been
   touched since 2022.
4. It solves the *picture*, and none of Karen's six requirements are the picture: stands, direction
   and moving players are all overlay.

### C. A 2D map drawn from the world's own geometry data

Project world (x, z) to map (u, v) with one affine transform, and draw the road, the stands, the
push arrow and the players as plain `Frame`s.

- **Open-source precedent for the overlay half:**
  [ShouxTech/roblox-minimap](https://github.com/ShouxTech/roblox-minimap) — *"Minimap system with
  markers for Roblox"*. **Licence: NONE declared (all rights reserved) — pattern only, no code
  taken.** **Maintenance: unmaintained**, last push 2021-04-21, 10 commits, 5 stars. It is a
  marker-over-a-map system, which is the shape; the licence is why not a line of it is copied.
- The same border-pinning rule as Etheroit's GUI above, and the same one **this repo already
  ships**: `Hud.Compass.offsetPx` returns `(x, onStrip)` and pins an off-strip marker to the end at
  `PINNED_TRANSPARENCY` rather than hiding it, *"so 'it is behind me and to the left' still has an
  answer"*.
- **The projection is the compass's arithmetic with a second axis.** `Compass.headingDeg` already
  fixes this game's convention — *"North is +Z and bearings run clockwise through east (+X)"*,
  `atan2(x, z)` and not `atan2(z, x)` — and that convention is what makes north-up unambiguous.

**Does well:**

1. **The geometry is already data, in one place, shared.** `ForestTest.roadZ(x)` is *"the one
   definition; every other reader calls this"*; `ForestTest.standPosition(index)` is where a hunter
   stands; `ForestTest.DRIVE_BEARING_DEG` / `PUSH_BEARING_DEG` / `PUSH_LABEL` are already the
   world's statement of direction and already read by the Hud through `Hud.driveBearing`. The DEV
   world has `Map.ROAD`, `Map.TAGS.shooterPost` and `Match.Markers.read`. **A map drawn from these
   cannot disagree with the world, because it is reading the same numbers the server places things
   from.** That is the one property option B lacks.
2. **Terrain is irrelevant** — nothing is rendered, only projected.
3. **Testable, and that is decisive here.** The projection is pure: studs in, pixels out. A spec
   asserts that the road's centre lands at the centre, that stand 1 and stand 9 land either side of
   it, that north is up, that a player 400 studs away pins to the rim. The previous project died of
   *"measured correct and looked wrong"*; here the arithmetic is provable and only the *look* needs
   Karen's eye — which is exactly her standing rule for this task.
4. Cheap on a phone: ~30 `Frame`s, built once, with ≤ 16 position writes at 20 Hz.

**Does badly:**

1. **It is a second description of the map** — the one real cost. Mitigated by reading the world's
   own module rather than re-typing its numbers: the map re-derives nothing (rule 3's spirit; it is
   the same rule that made `ForestTest.DRIVE_BEARING_DEG` a stated value rather than a HUD
   calculation).
2. **It shows only what the world has stated.** No trees, no rocks, no terrain shading — a schematic,
   not a satellite photo. For Karen's six requirements that is sufficient; for "it looks like a real
   game map" it is not, and that is a later, separate task (an image *under* the overlay, option B,
   when the map stops moving).
3. A world that states no geometry gets an empty map. Must degrade to "no map" visibly, not to a
   blank panel.

## The pattern adopted, and why

**Option C: a 2D map drawn from the world's own geometry, with the overlay conventions borrowed
from the two open-source minimaps (team-coloured blips, border-pinned when out of range,
player-centred, north up).**

The decision is forced, not preferred, and the forcing fact is one line:
**our ground is Terrain, and a ViewportFrame cannot render Terrain.** Option A — the one the
official docs recommend for exactly this use case — would draw a void. Option B is a picture of a
map that is still being built this week, behind an upload and a subscription. Option C reads the
numbers the server already places the road, the stands and the beaters from, which is the only one
of the three that **cannot be wrong about where they are**.

**Borrow before building (rule 2):** nothing here is invented. The projection is `Compass`'s own
bearing convention with a second axis; the pinning rule is `Compass.offsetPx`'s, which is also
Etheroit's *"pinned ... stick on the border"*; the team-coloured marker-over-map shape is
ShouxTech's. **Nothing is copied as code** — neither source grants a licence (one declares none,
one is a forum post) — and the two things that ARE licensed for copying (the Roblox docs' MIT code
samples, CC BY prose) describe option A, which we are not using. What is being written new is
arithmetic this repo already contains for one axis.

**What is deliberately NOT built**, so a later task does not read this as a gap:

- No ViewportFrame, ever, while the ground is Terrain.
- No map image. When the map stops moving, an `ImageLabel` can go *under* this overlay without
  changing it — the projection is the seam.
- No rotating minimap. **North up**, both sizes: the compass strip already owns "which way am I
  facing", the world's own direction facts are written as bearings from north, and a rotating map
  needs a second heading source — a second writer of the same question (rule 3). `Compass` reads
  `Camera.viewHeadingDeg` and three tasks were spent getting that one right (task 125 rounds 3-4);
  the map re-deriving it is how that bug comes back. The player's own marker carries a facing
  wedge instead, which gives "which way am I pointing" without turning the picture.
- No fog of war, no boars on the map. Boars are the thing she is hunting; a map that shows them is
  a different game. (And `Report`'s kill log already answers "what did I get".)
