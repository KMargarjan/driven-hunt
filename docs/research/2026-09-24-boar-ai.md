# Boar AI (grey box, v1) — research note

Rule 1. Written before any boar code. System: ROADMAP.md step 1.2, TASKS.md Task 18.
Date: 2026-09-24.

## What the system must do

One boar, in the Task 17 test arena (400×400 studs, ground surface at y = 0).

1. **Spawn** at a spawn point in the arena. Body: a grey box of boar size, **unanchored** and
   physically simulated, **server-owned** so a client cannot push it.
2. **IDLE** — slow wander/graze inside a home area.
3. **FLEE** — when a player comes within a detection radius, run away from that player, around the
   cover blocks, at boar sprint speed, reacting within 0.5 s.
4. **ROUTE** — while fleeing, head for the far edge of the arena (the future shooter line), not just
   directly away from the threat.
5. **DESPAWN** — on reaching the exit edge or leaving the arena, remove the boar and fire a signal
   (the score system will need it).
6. One owner module for boar state (rule 3), and the "who scares the boar" test must be **one
   function**, so drivers-only can be plugged in later without touching the state machine.

Later, out of scope here: dogs, several boars, hit zones, wounded running (ROADMAP Milestone 1.5).

## Numeric targets

| Quantity | Value | Where it comes from |
|---|---|---|
| Sprint speed | **38 studs/s** | A wild boar tops out at ~40 km/h ([Mossy Earth][boar1], [Speed of Animals][boar2]). Roblox's convention is ~0.28 m per stud, but the project's own scale is "1 stud ≈ 1 m" for a 1.5 × 1 × 0.6 stud body, so 40 km/h ≈ 11 m/s would look glacial across a 400-stud arena. 38 studs/s is the Director's suggested 35–40 band and reads as a sprint at this scale. **A feel number: Karen decides it in a playtest.** |
| Wander speed | **4 studs/s** | Director's suggestion. Grazing pace, ~1/10 of sprint. Feel number. |
| Detection radius | **40 studs** | Director's suggestion. 1/10 of the arena's span, so a boar reacts well before a player is on top of it. Feel number. |
| Reaction time | **≤ 0.5 s** | Director's requirement. Achieved by sensing every `SENSE_INTERVAL` = 0.2 s, so worst case is 0.2 s plus one frame. |
| Home area | **120-stud radius around the spawn point** | Big enough that grazing does not look caged, small enough that an idle boar stays where a drive can find it. Feel number. |
| Despawn edge | **z ≤ −190** (the north edge, 10 studs inside the plate) or any exit from the arena bounds | The arena is ±200; the shooter line will sit on the far side from the Task 17 spawn pad (z = +170). |
| Repath interval | **0.5 s while fleeing** | Cheap enough for one boar; `Path:ComputeAsync` is a yielding call. Revisit when there are many boars. |

Every one of these lives in one `CONFIG` table in the owner module.

## Sources

### 1. Roblox `PathfindingService` and the pathfinding guide — the engine's own navmesh
- <https://create.roblox.com/docs/reference/engine/classes/PathfindingService>
- <https://create.roblox.com/docs/characters/pathfinding>
- Licence: Roblox documentation, first-party; the API itself ships with the engine. Maintenance:
  actively maintained by Roblox.
- **Good:** `PathfindingService:CreatePath(agentParameters)` then `Path:ComputeAsync(start, finish)`
  and `Path:GetWaypoints()` give a route around obstacles with no navmesh work of our own.
  `AgentRadius`, `AgentHeight`, `AgentCanJump` and `Costs` tune the agent; `Path.Status` reports
  `Enum.PathStatus.Success`; `Path.Blocked` fires with a `blockedWaypointIdx` so we can recompute
  only when the obstacle is *ahead* of us. A `PathWaypoint` carries `Position`, `Action` and `Label`.
- **Bad:** it is built around `Humanoid:MoveTo`. The docs say the service itself is not restricted to
  humanoids, but for any other agent "you'd need to implement custom movement logic". It is also
  asynchronous and yields, and it returns a *static* route — nothing steers or avoids anything
  between waypoints.

### 2. SimplePath (grayzcale) — the community wrapper everyone uses
- <https://github.com/grayzcale/simplepath> · forum thread
  <https://devforum.roblox.com/t/simplepath-pathfinding-module/1196762>
- Licence: **MIT**. Maintenance: no archived or deprecated notice; ~176 commits; the definitive
  repository is ambiguous (several near-identical forks: `ahmicy/simplepath`,
  `LuaRook/RBLX-SimplePath`, `MohhayScripts/RBLX-SimplePath`, `cebar2002/RBLX-SimplePath`), which is
  itself a maintenance risk.
- **Good:** wraps exactly the loop we would otherwise write — compute, walk the waypoint list,
  re-compute on `Path.Blocked`, give up after N failures — and explicitly supports
  "humanoids and non-humanoids".
- **Bad:** it is a *waypoint walker*, so it still assumes something that moves the agent; we would
  keep our own mover anyway. Vendoring it means a Wally dependency (it is not on Wally under a
  single canonical name) or a copied file, and picking one of several forks. For one boar and one
  state machine, the wrapped part is ~40 lines.

### 3. Craig Reynolds, *Steering Behaviors For Autonomous Characters* (GDC 1999 / SIGGRAPH 97)
- <https://www.red3d.com/cwr/steer/gdc99/>
- Licence: a published paper, freely readable; we take the **technique**, not code. Maintenance: it
  is a 1997/1999 paper and does not change — it is the standard reference, cited by essentially
  every game-AI text since.
- **Good:** defines exactly the behaviours this task names. **Flee** is "the inverse of seek",
  steering away from a point. **Wander** is the important one: rather than a new random force each
  frame, you "retain steering direction state and make small random displacements to it each frame",
  which is what makes wandering look like an animal instead of a twitching cube. **Obstacle
  avoidance** keeps "an imaginary cylinder of free space in front of the character".
- **Bad:** pure steering has no map knowledge, so it walks into dead ends behind our cover blocks.
  It complements a navmesh; it does not replace one.

### 4. Roblox network ownership — why the boar must be server-owned
- <https://create.roblox.com/docs/physics/network-ownership>
- Licence: first-party documentation. Maintenance: actively maintained.
- **Good:** states the rule we need directly — "you can manually call `SetNetworkOwner(nil)` for the
  server for gameplay-critical objects that the client should not be able to manipulate".
- **Bad / the trap:** "the server always owns anchored BaseParts and **you cannot manually change
  their ownership**". So calling `SetNetworkOwner` on an anchored part **errors**. The boar body must
  be unanchored (which the task requires anyway), and the call must happen on the server on an
  unanchored assembly.

### 5. `LinearVelocity` — the mover
- <https://create.roblox.com/docs/reference/engine/classes/LinearVelocity>
- Licence: first-party. Maintenance: current (the modern constraint; `BodyVelocity` is the legacy
  one).
- **Good:** `VectorVelocity` + `MaxForce` + `RelativeTo` drives an unanchored assembly at a chosen
  world velocity while physics still resolves collisions, so the boar is pushed around by the world
  rather than teleporting through it.
- **Bad:** with `VelocityConstraintMode.Vector` it fights gravity unless the Y component is left
  free; we drive X/Z and let gravity own Y.

## Pattern adopted, and why

**Navmesh route + steering follow + one injectable sense function.** Nothing invented:

- **Route** from `PathfindingService` (source 1), recomputed on a timer and on `Path.Blocked` ahead
  of us. This is what gets the boar *around* the Task 17 cover blocks, which steering alone cannot do
  (source 3, "Bad").
- **Movement** by steering toward the next waypoint and writing `VectorVelocity` on a
  `LinearVelocity` (source 5). This is the "custom movement logic" the Roblox guide says a
  non-humanoid agent needs (source 1).
- **Wander** exactly as Reynolds describes (source 3): keep a heading, jitter it slightly each step,
  and steer back toward the home centre when the boar reaches the home radius. Not a fresh random
  vector per frame.
- **Flee direction** as Reynolds' flee (source 3), but blended with the ROUTE requirement: the
  destination is the exit edge, biased sideways away from the threat, so the boar runs *through* the
  arena toward the shooter line instead of into a corner.

**Not borrowing SimplePath (source 2), with a reason (rule 2).** Three: (a) its value is the
waypoint-walking loop, but we need our own mover anyway for an unanchored non-humanoid box, so the
saving is ~40 lines; (b) there is no single canonical repository — at least four near-identical forks
exist and none is clearly *the* one, which is a supply-chain and maintenance risk on a public repo;
(c) it is not on Wally under a canonical name, so adopting it means vendoring a copied file, which is
worse for review than calling `PathfindingService` directly. If boar counts grow and repathing
becomes the bottleneck, revisit — the wrapper is the right shape, the provenance is the problem.

**Testability is part of the pattern, not an afterthought.** The previous project died partly of a
harness that was wrong as often as the game (PROJECT_CONTEXT.md). So the state machine takes its
world through injected dependencies — a body, a sense function, a pathfinder and a clock — and
advances with an explicit `step(dt)`. Server specs drive it with a fake body and a fake player
position and assert the state transitions directly, with no physics and no waiting. A separate,
small set of assertions covers the real spawned boar (unanchored, server-owned, inside the arena).

**One function decides who is a threat.** `CONFIG.isThreat(player)` — today "every player", later
"drivers only" — so teams plug in without touching the state machine (the task's requirement).

## Addendum, 2026-09-24 (Builder, Task 18) — what the design changed and what I confirmed

The Architect's design `docs/design/boar-ai.md` (verdict `PASS`) is what the code is built to. Rule 1
keeps decisions and dated measurements here, so:

### 1. The scale premise above is wrong. 1 stud = 0.28 m, not 1 m

The "Numeric targets" table says "the project's own scale is 1 stud ≈ 1 m" and calls 38 studs/s a
feel number in tension with physics. **That is superseded.** Roblox's own units page states the
conversion outright: "1 stud" = "28 cm" (and 1 RMU = 21.952 kg) —
<https://create.roblox.com/docs/physics/units>. I fetched the page and read the table.

At 0.28 m/stud, 40 km/h = 11.1 m/s = **39.7 studs/s**, so `SPRINT_SPEED = 38` is not a compromise,
it is the physically correct figure and it lands inside the Director's 35–40 band. The same
correction resizes the body: this note's "1.5 × 1 × 0.6 stud" boar would be 42 cm long. A real
1.5 m × 0.9 m × 0.5 m boar is **5.5 × 3 × 2 studs**, which is what `CONFIG.BODY_SIZE` uses. It also
explains the sanity check: a default Roblox character is ~5 studs tall, i.e. ~1.4 m, not 5 m.

Everything else in the targets table stands. `SPRINT_SPEED`, `WANDER_SPEED`, `DETECT_RADIUS`,
`HOME_RADIUS` and `CALM_TIME` remain **feel** numbers for Karen regardless of the arithmetic.

### 3. Where the code departs from the design, and why

Both are degenerate cases where the formula as written does not do what the surrounding text says.
The code carries the arithmetic in a comment at each site, and they are claims in the review request.

- **`onExitSide`.** The design writes `(c.Z - exitZ) * sign(exitZ - position.Z) > 0`. With the boar at
  z = 0, the exit at z = −190 and the threat at z = −60 — the threat squarely in the way — that is
  `130 * −1 = −130`, i.e. false, so the doubled side-bias would never apply in the one case it exists
  for. `src/server/Boar/Brain.luau` uses `(c.Z − position.Z) * (exitZ − position.Z) > 0` instead.
- **The home pull.** The design writes `heading = unit(heading + toHome * HOME_PULL)`. When the
  heading points exactly away from home that is `(−toHome) + 0.6·toHome = −0.4·toHome`, whose unit
  vector is the original heading: the boar never turns round. The code rotates the heading toward
  home by at most `HOME_PULL` radians per sense tick, so `HOME_PULL` is now an angle, not a weight.

Two more departures came out of review round 2, finding 6, and belong here rather than only in a
review request (which is rewritten per task and is not a durable record):

- **`escaped` is a FLEE outcome.** The design (§5, "Despawn") says `position.Z <= field.exitZ` →
  `escaped`, evaluated in every state. That let an **idle** boar delete itself: nothing forbids a
  wander from crossing the line, and the grey box would lose its only boar with no driver anywhere
  near. `Brain._outcome` now requires `self._state == "FLEE"`. Leaving the arena bounds, or falling
  through the world, is still `outOfBounds` in any state, so a boar can never be stranded outside.
- **`spawnPoint` moved from `Vector3.new(-40, 0, -60)` to `Vector3.new(-40, 0, 20)`.** The design's
  point is 130 studs from `exitZ = -190`, while `HOME_RADIUS` is 120 and the wander assertion
  tolerates excursions to 140 — so the numbers contradicted each other. The new point is 210 studs
  from the exit line and still clear of `PillarMid` at (40, −40) and `WallWest` at (−60, −100).

Both are asserted: `boar_brain.spec` requires that an idle boar at the real `CONFIG.spawnPoint` in
the real `CONFIG.field` never despawns over 120 simulated seconds, and that an idle boar sitting past
the exit line is not despawned, while a *fleeing* one crossing it is.

A fifth departure came out of the first real harness run (2026-09-25):

- **The live spec no longer asserts `pathFailures == 0`.** The design (§10, live-spec assertion 8)
  requires "`stats().pathRequests > 0` and `pathFailures == 0` — so a silent permanent fallback to
  straight-line flee is a failure, not an invisible degradation", and §13 rests an open risk on it.
  **Measured:** on the spec's own plate, floating at y = 500 in an otherwise empty region, 36 of 37
  requests return `Enum.PathStatus.NoPath`. An Edit-mode probe with the same `CONFIG.AGENT`
  parameters returns `Success` with 53–54 waypoints at y = 0. So that assertion was asserting a
  property of **Roblox's navmesh on a floating platform**, not of this code.

  The design's *intent* is kept, by two replacements rather than a deletion: the plate test asserts
  that the boar asked for paths, that it still sprinted, escaped and despawned on the Reynolds
  fallback alone, and that **every** failure reason is `NoPath` (a per-reason count, because one
  overwritten "last reason" slot hid rarer failures — review round 4, finding 2); and a **new test
  routes across the real arena** at y = 0 and requires the route to leave the straight line by more
  than 15 studs, which only going around one end of the 80-stud `WallWest` can do. That second test
  is the one that actually protects against a silent fallback, and its first version did not: it
  never waited for the arena and so measured a straight line over the default Baseplate.

### 4. What is measured now, and what is still not (rewritten 2026-09-25)

This section was written while nothing had ever run. Karen connected Studio on 2026-09-25 and the
harness went green — `[harness] PASS: 24/24 checks @ <code commit> (clean tree)`, 39 server and 4
client assertions — so three of its four statements are now false and are replaced here rather than
left to mislead (review round 4, finding 4).

**Now measured:**

- **The mover configuration works.** `LinearVelocity` in `Plane` mode with the tangent axes X and Z
  does leave Y to gravity: the boar falls its `SPAWN_CLEARANCE`, lands, and is asserted resting
  within 0.6 studs of `groundY + BODY_SIZE.Y / 2` with `|velocity.Y| < 1`. The design's
  `ForceLimitMode`/`MaxAxesForce` fallback is not needed and is not in the code.
- **`AlignOrientation` keeps it upright.** `CFrame.UpVector.Y > 0.9` holds throughout a sprint.
- **`PathfindingService` returns a usable path where the game plays**, and does not on the spec's
  floating plate. See §3's fifth departure for the numbers.
- **Every spec has executed.** The boar spawns, idles below `WANDER_SPEED * 1.5`, reaches half sprint
  speed within 1 s of a threat, grows the flat gap by ≥ 20 studs, and despawns exactly once as
  `escaped`.
- **Rule 5 is met.** Three play-time screenshots were captured through MCP and inspected. They also
  found the one thing the tests cannot see: the arena's ground plate **was** coplanar with the
  default `Workspace.Baseplate` and lost the depth test over half its area, so the 400x400 square
  rendered as a triangle. **Fixed in Task 22** (2026-09-25): Karen had the Baseplate and the second
  `SpawnLocation` archived out of `Workspace` (`backups/2026-09-25_workspace-defaults.md`), and the
  plate now renders as a full square. The same screenshots showed the boar's sides reading
  near-black, which Task 22 fixed in `Boar.CONFIG.BODY_COLOR`.

**Still not measured:**

- **`Path.Blocked` has never fired.** The `consumed() + 2` index comparison in
  `Runtime:_requestPath`'s `onBlocked` is unexercised: the plate returns `NoPath`, and in the arena
  no threat ever appeared, so no boar pathed under load. `stats().pathBlocked` exists to make it
  visible when it does.
- **No real player has ever been a threat.** Every threat in every test is an injected
  `{ id, position }` record, so `CONFIG.isThreat` → `Players:GetPlayers()` →
  `character.PrimaryPart` is unexecuted.
- **`maxBoars` is never reached**, and `Runtime:destroy` runs in `afterAll` but nothing asserts on
  what it leaves behind.
- **Nothing has run with more than one boar, or with two players.**

### 5. What review round 1 changed (2026-09-24)

The Reviewer found six things; three were defects in this task's code and specs, three were false or
unrecorded statements. The code ones:

- **`Path.Blocked` was documented but not implemented**, and a new `Path` object was created per
  request, both contrary to the design. Now `defaultWorld` keeps **one `Path` per agent**, connects
  `Path.Blocked` once, and reports the blocked index to the Runtime, which forces a repath only when
  that index is still ahead of the boar. `Brain:consumed()` exists for exactly that comparison, and
  `Runtime:stats().pathBlocked` counts it. `releasePath(agentId)` drops the `Path` on despawn.
- **The anti-stuck 90-degree turn was dead code**: it was written onto `Brain._heading`, which
  `_fleeDirection` reads only as the degenerate fallback of `unit()`, so in the case it exists for
  the value was never used. It is now applied to the direction actually returned, the stale route is
  dropped with it, and `boar_brain.spec` asserts that a pinned boar turns.
- **`boar_body.spec` would have failed on its first real run for the wrong reason**: it measured the
  full assembly speed while the boar was still falling the `SPAWN_CLEARANCE` 0.5 studs, which peaks
  near 14 studs/s at Roblox's 196.2 studs/s^2 — well over the 8 studs/s the idle assertion allowed.
  It now waits for the body to land and measures flat XZ speed.

The pathfinding agent parameters moved into `CONFIG.AGENT`: they are tunables (they decide whether
the navmesh will route a 2 x 3 x 5.5 body past the cover blocks), not structure, so "every number is
in one table" is true again.
