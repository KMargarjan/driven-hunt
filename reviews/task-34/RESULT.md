1. `src/server/Weapon/Hardware.luau` / `Hardware.give` with `src/server/Weapon/init.luau` / `Weapon.grant`, `watchPlayer`, the sweep — **the grant is no longer atomic, so one player can be given two Tools, one of which nothing owns.** Evidence: `give` is now `local backpack = player:FindFirstChildOfClass("Backpack") or player:WaitForChild("Backpack", 5)` — it yields. `grant` writes the record only after it returns: `local tool = Hardware.build() … watchTool(player, tool) … if not Hardware.give(tool, player) then … end; tools[player] = tool`. While that wait is parked, `holdsTool(player)` returns `false`, so `armingAction(mayArm, holdsTool)` is `"grant"` for every other caller. Two callers fire in exactly that window: the new hook `player.ChildAdded:Connect(function(child) if child:IsA("Backpack") then Weapon.refreshArming(player) end end)` is triggered by the very event `WaitForChild("Backpack")` is waiting for, and the sweep (`ARMING_SWEEP_SECONDS = 2`) runs during any wait longer than 2 s. Both then build and parent a second Tool into the same Backpack. The comment asserting otherwise — "refreshArming grants only if they are allowed one and are not already holding it, so this is idempotent" — is false while a grant is parked. Consequences, all game-visible: `tools[player]` names one Tool and the other is untracked, so `Weapon.revoke`'s `Hardware.destroy(tools[player])` cannot remove it and a player the drive says may **not** carry a gun keeps one (the `mayCarryWeapon(player) == holdsGun(player)` invariant `match_live.spec` and `match_teams.spec` now assert); and with `CONFIG.AUTO_EQUIP = true` the player can end up holding the untracked Tool while `watchEquipped` syncs `equipped` from the recorded one, so `state.equipped` is `false` and every Fire is refused while a shotgun is visibly in their hands. Required: make arming one writer per player for the whole operation — reserve the player before the wait and re-check after it, or drop the wait entirely and let the `ChildAdded` re-grant cover the same moment (it was added for exactly that) — and ensure at most one `Shotgun` Tool exists per player, adopting or destroying any other.

2. `src/server/Weapon/init.luau` / `Weapon.refreshArming` and `src/server/Match/init.luau` / `applyRefreshArming`, `dispatch`, `Match:step` — **`refreshArming` is now a yielding call, and the drive applies it synchronously inside its Heartbeat step, which has no re-entrancy guard.** Evidence: `Phase.enterAssigning` emits `{ kind = "placePlayers" }` then `{ kind = "refreshArming", userIds = userIds }` in one effect list; `applyEffects` → `applyRefreshArming` → `world.weapon.refreshArming(player)` → `Weapon.grant` → `Hardware.give` → `WaitForChild("Backpack", 5)`. `Match:step` is `RunService.Heartbeat` (`heartbeat = RunService.Heartbeat:Connect(function(dt) Match:step(dt) end)`), sets `accumulator = 0` and calls `dispatch` with `MATCH_STEP_HZ = 4`, so a 5 s park lets ~20 further `dispatch` calls mutate `state` and apply their effects while the parked one is still holding stale `before`/`driveBefore` — and `dispatch`'s own comment is "a dispatch inside a dispatch would apply effects out of order". On resume that parked thread can fire `phaseSignal` for a transition that already fired and re-run the `Assigning` block (`stats.drives += 1`, `board = Score.new()`) for one drive. The drive was designed around effect application never blocking: `Body.place` is a `CharacterAdded` connection plus `task.delay(config.PLACE_TIMEOUT, …)` precisely so `LoadCharacter` does not hold the step (design §5.3). Required: the Backpack wait must not run on the caller's thread — retry from the weapon's own thread (the sweep or the `ChildAdded` hook already re-ask) and keep `refreshArming` non-yielding, since it is a published interface the drive calls (`docs/design/drive.md` §8.5).
