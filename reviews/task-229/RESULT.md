1. `src/client/Hud/ShopPanel.luau` / `ShopPanel.buildRoleSwitch` — the segmented control is built `Visible = false` and nothing in the repository ever sets it true, so on BOTH surfaces the two halves are never rendered and cannot be pressed. The block's eyebrow and caption appear; the control itself does not. Evidence: `buildRoleSwitch` does `local track = frame(parent, "RoleSwitch", zLift)` then `track.Visible = false`, and `frame` returns a plain `Frame` whose children (the two `TextButton` halves, their `Word`, `Rim` and `Underline`) are parented to that track. Grep of `src/` for `RoleSwitch|roleSwitch|rowSwitch|detailSwitch` finds every writer of the track: `relayout` writes `rowSwitch.track.Position` / `.Size`, `detailSwitch.track.Position` / `.Size` and `roleSwitch.track.Position` / `.Size` (`PadPanel.relayout`), and `ShopPanel.paintRoleSwitch` writes `switch.track.BackgroundTransparency` — no `Visible` write anywhere. Only the HOLDERS are shown (`block.Visible = tall`, `pane.Visible = surface == "detail"`, `block.Visible = out.switchShown`), and a Roblox `GuiObject` with `Visible = false` is not rendered and takes no input however visible its parent is. This file's own idiom proves the omission: `buildButton`'s progress bar is built the same way (`track.Visible = false`) and then flipped by `(buyProgress :: Frame).Visible = kind == "locked"`. The specs cannot catch it: `pad_panel.spec`'s `lights the half the SERVER chose, and the words are the data's` asserts `block.Visible` (the `RoleBlock` holder), `roleLit()`, `switchText()` and, in `puts the two halves above the block's own labels`, `half.ZIndex` / `half.Text` — never `track.Visible`; `shop_panel.spec` does the same. This is REQUEST claim 10 (*"the segmented switch is built and painted ONCE ... and PLACED by whichever panel owns the rectangle"*) and `docs/design/role-switch.md` §10.8 / hazard 5 not being true as built. Required: the one writer of each surface's rectangles must write the track's `Visible` with the holder's (`relayout` in both modules), and a case in `pad_panel.spec` and `shop_panel.spec` must assert the track and a half are visible off the BUILT instances when the block is shown, and not when it is not.
2. `src/client/Hud/ShopPanel.luau` / `ShopPanel.select` — the selected item is an input to `switchSurfaceFor`, but a selection change never re-lays out, so the detail (phone) surface is never shown on the player's path and goes stale if it ever is. Evidence: `switchSurfaceFor` answers `"detail"` only `if id == ShopData.ITEM.ALWAYS_HUNTER`; `detailBlock`'s visibility is written in exactly one place, `relayout`'s `pane.Visible = surface == "detail"` (with `status.Visible = surface ~= "detail"` beside it); `ShopPanel.select` is `selected = id; stats.selects += 1; ShopPanel.showPicture(id); ShopPanel.render()` — no `relayout`. The only callers of `relayout` are `build`, `setOpen(true)`, `setRoleWish` when `(was == nil) ~= (wish == nil)`, and `step` when `screenSize() ~= screenWas`. In `setOpen` the relayout runs BEFORE the selection is set (`ShopPanel.relayout()` ... then `if selected == nil then ShopPanel.select(firstId())`), and `firstId()` returns the first row with `row.buyable == true`, which an owner's `ALWAYS HUNTER` row is not — so for the man this feature is for, the surface at relayout time is `"none"`, and tapping the row afterwards changes nothing. On a TALL viewport (panel width < `WIDE_AT` 520) the shop's switch therefore never appears, which is the surface `docs/design/role-switch.md` §14.2 makes the way in on a short screen; and in the reverse direction a block shown by a resize stays shown, with the status row still hidden, after the selection moves to another item. No spec covers it: `shop_panel.spec`'s `hides both surfaces for a man who owns nothing, and shows one when he does` calls `Panel.relayout()` by hand and then asserts only `if Panel.layoutFor(0, 0).mode == "WIDE" then expect(block.Visible).to.equal(true)` — the detail pane's visibility is never asserted off the built instances at all. Required: `select` must drive the one rectangle writer when the surface can have changed (or the surface must be decided somewhere that runs on selection), plus a case that drives `select(Shop.ITEM.ALWAYS_HUNTER)` on a TALL viewport and asserts `RoleBlock` in the detail column becomes visible and the status row hidden, and that selecting another item puts both back.
